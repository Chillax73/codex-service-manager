# 第一轮验证报告

日期：2026-10-12（原型阶段记录；当前产品结果见 [正式验收](../docs/results/VALIDATION.md)）

## 结论

服务控制机制可行。真实本机进程、单容器及 Compose 的启停/重启已实测通过；项目及 5 个 hooks 的审核已在用户授权下完成，已捕获 CLI 会话的实际 SessionEnd 事件。Codex 桌面自动登记和真实应用退出仍未通过端到端验证。

共 25 项检查通过：22 项真实进程/容器实验，3 项策略模拟。初次配置发现识别了 5 个未信任 hooks；之后通过正常审核界面完成信任并核对启用状态。审核与 CLI 生命周期检查另记录在 hook-trust-results.json，不混入前述服务实验计数。

## 初始接入阻碍与审核结果

首次探测时，本机 Codex 配置接口返回：

> 项目尚未被信任：请通过 Codex 正常信任流程允许当前项目加载配置、hooks 和执行策略。原始诊断中的个人路径仅保留本机。

项目配置已安装在 `.codex/hooks.json`。用户随后授权代为审核，已通过正常 Folder access 和 hooks 浏览器完成当前项目及 5 个 hooks 的信任。配置接口核对全部 trusted/enabled，项目层已加载；没有使用绕过信任选项。事件脚本仅记录本地元数据。

关闭两次本地 CLI 测试会话后，收到两条真实 SessionEnd 记录。当前桌面聊天执行 hook-probe 成功，但没有对应 PreToolUse/PostToolUse 记录；现有桌面会话是否需要重新加载配置或是否支持同样 hooks 尚未确证。详见 `hook-trust-results.json`（仅本机原始证据）。

## 初次失败及修复

初次进程实验停止时，发送退出信号后继续调用 killpg(..., 0) 返回 Operation not permitted，监督进程异常结束、历史未收尾。原始证据保留在 initial-process-failure.json。原型改为检查仍存活的进程组成员，并确保清理异常写入历史；相关实测重新运行后通过。

## 清理与范围

- 最终本机服务实验和跨工具调用实验的测试进程均已停止。初次失败实验的旧 PID 与子进程另由 cleanup-results.json 检查。
- Docker 新建测试容器、Compose 网络和测试数据卷已删除；容器测试前后的已有容器状态比较一致。
- 验证启动了原本未运行的 Docker Desktop，实验完成后执行了 docker desktop stop，恢复原本状态。
- 已有容器未变的比较基准是在 Docker 引擎启动后建立的，不代表引擎启动本身没有触发已有容器的启动策略。
- 仅在本机 127.0.0.1 发布测试端口；使用已有 python:3.12-slim 镜像，没有拉取镜像。
- 保存了最小原型及证据，没有实现 Mac 界面、完整插件或原生应用退出监听。

## 对实现方案的影响

建议以独立服务管理进程负责启动配置、进程身份、日志和历史；Codex 插件调用统一入口。Hooks 可用于补充归属与生命周期信息，其桌面事件覆盖和时序仍必须实测。

普通命令的自动发现尚未证明可可靠接管；SessionEnd 不能直接等同退出应用。Docker 的控制能力已验证，但还需接入统一模型和运行记录。

官方依据：[Hooks](https://learn.chatgpt.com/docs/hooks)，其中审核信任、工具事件时序和 SessionEnd 语义与本机配置探测结果共同支持上述判断。
