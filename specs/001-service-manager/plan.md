# 实现设计

## 架构

原生 `.app`（SwiftUI 工作区 + AppKit 菜单栏）→ JSON stdin/stdout RPC → Python 标准库管理引擎 → SQLite WAL。

每个经配套入口启动的本机运行由独立监督进程持有子进程，脱离启动工具和 UI 生存。监督进程负责信号、输出滚动、自然完成和退出码。管理请求通过文件锁串行写入；读操作独立，GUI 在后台执行不阻塞主线程。

独立原生观察器订阅 NSWorkspace 应用终止，按 bundle ID 与实例集合判断最后实例退出，再调用引擎批量结束。观察器无需模型、无需聊天 Hook；SessionEnd 从不作为退出信号。退出观察器有独立 PID/身份状态和日志。

Docker 适配器使用明确容器 ID、Compose project/service/config_files/working_dir 标签与保存配置核对对象；引擎不可用时保留历史并显示未知。Compose 组展开成员，统一批量操作，每个成员只执行一次。

配套入口 `scripts/csm` 提供 launch / container / compose / list / stop / restart 等命令，cwd 自动成为项目。项目接入安装器加入带边界标记的 AGENTS.md 段落（可移除），要求 Codex 服务启动走该入口。接入文档随项目分发，不要求依赖未证实的 hooks。

## 任意本机聊天自动观察（2026-10-12）

新增用户级 PreToolUse/PostToolUse hook 与独立采集组件。PreToolUse 在原命令前后加入 arm 检查点，通过本机临时目录的 0600 FIFO 将 shell 父进程身份发送给采集器，避免在业务沙箱里访问数据库或进程表。末尾检查点在 shell 退出前记录直接后台子进程，并用独立变量保留原命令退出码；显式 exec/exit 维持原行为、跳过末尾检查点。保留原命令文本、shell、cwd、stdin/stdout；arm 失败不阻止业务命令。不对 write_stdin 重复插入。工具命令仅临时识别 Docker/Compose 启动信息，持久化事件只含白名单元数据，不保存完整命令/输出/聊天或环境。

采集组件通过 scripts/csm 作为内部后台任务启动，使用状态目录作稳定 cwd，并持有单实例锁。有跟踪进程或近期 Docker 事件时，采集轮次之间等待约 0.5 秒，空闲时等待约 5 秒。FIFO 中的新检查点可立即唤醒。采集器按 PID 和出生身份跟踪已验证的后代，跨父进程变更保留关联。监听进程按实际 PID 去重，一次脚本产生多个监听进程分别记录，已由配套入口管理的进程排除。持续约 30 秒的无监听叶子进程列为后台任务。Compose 关联需实际标签与启动上下文匹配，单容器需工具返回的容器 ID。Docker 观察只读取白名单字段。组件独立于管理窗口和聊天运行，UI 展示心跳和恢复入口。

自动观察服务继续使用 services/runs，spec 增加 management=observed、source=global_hook、归属依据；runtime 保存实际 PID/出生时间或容器 ID。状态刷新不依赖监督进程，进程退出记录结束时间但未知退出码；不恢复之前未采集日志。首阶段控制请求由后端拒绝；本轮改为独立能力，手动批量按能力执行，原运行结束策略跳过。后台内部采集任务从常规列表排除，状态通过 metadata 展示。采集器状态文件和事件均在状态目录并受 0700/0600 权限保护。

用户级安装器保留无关 hooks、首次备份、只移除自己的 handler，不写信任数据库，不改业务项目。验证先实测当前桌面回调，再验证跨项目、脚本多进程、直接容器/Compose、去重、身份变化、观察器恢复和实际窗口。无法在当前聊天自动重新加载用户配置时保留安装结果，并明确需要正常审核和新聊天的验收边界。

## 旧聊天与后台发现：待实施设计

旧聊天复查已发现：配置检查能看到两个 trusted/enabled handler，采集器心跳正常，但同一旧聊天的后续启动没有 arm 检查点或采集事件。换窗口继续旧聊天不等于加载新配置。`check_capture_hooks.py` 启动独立短时 app-server 读取配置，不连接桌面共享运行时，也不能确认或修复旧聊天加载状态。

下一步先评估正常共享运行时配置重载接口，实测同一旧聊天的无害命令和测试服务；目前没有可对用户承诺的重载命令。不得通过编辑信任数据库或放宽沙箱实现重载，不能直接退出 Codex 作为无副作用的修复（退出可能触发已管理项目的结束策略）。

后台发现兜底仍待实施：基于实际进程身份、cwd 和指定容器标签产生候选，保留独立的发现来源与归属依据；仅凭端口、可执行名称或时间不能标为 Codex 启动。证据不足保留在发现列表，不能伪造启动事件或事后完整历史。首轮需验证旧聊天启动、原有对象、多项目/worktree、无关进程排除和已退出对象，再扩展包装脚本与脚本内部 Docker。

复杂脚本重启另行实施，只有确认控制对象、必要环境与启动方式后才升级为已管理；自动观察本身不改变业务进程的存活方式。旧聊天与后台发现仍未交付；普通启动接管的常见路径与显式配置已按下节实施，任意复杂包装自动拆分仍待扩展。

## 普通启动接管实施

新增 adoption 模块：按采集关联、PID/出生身份、实时父子树及其他服务范围生成停止计划。逐个复核后向启动器和子进程发信号，不使用共享 killpg；超时保存停止失败及已确认成员，支持显式强制停止。端口只用于停止后核验，不作为认领依据。

PreToolUse 保守识别无 shell 运算、展开、环境赋值或敏感参数的常见单项启动，保存 argv 候选。arm 只传递 PATH/LANG/JAVA_HOME 白名单。候选只有匹配实际启动器且范围不含其他监听服务时才能重启；未知包装不猜测。configure_observed RPC/CLI/原生表单可补齐显式配置。

observe 输出独立能力和 capability_reason；operate 每次重查。旧运行按观察身份控制，新运行使用监督器并升级为 managed；采集器不得覆盖监督运行。手动批量按能力执行，项目结束触发继续跳过观察对象。

隔离真实测试覆盖旧记录、直接启动、包装进程、复杂脚本、身份变化、停止失败、历史/去重、隐私和实际 UI。正式业务服务只读核对，不用于测试停止。

## 数据模型（现有）

- projects(id, cwd 唯一, name, manual, codex_exit)
- services(id, project_id, name, kind, spec JSON, keep, group_id)
- runs(id, service_id, started, ended, state, exit_code, runtime JSON, error, log)
- operations(id, service_id/project, action, trigger, started, ended, result, error)
- metadata(key, value) 保存观察器状态/事件。

必要环境字段受本机文件权限保护。启动配置的只读展示应隐藏 env 值。

## 接口

`engine.py rpc` 从 stdin 读取单个 JSON `{action, ...}`，stdout 输出 `{ok, result}` 或 `{ok:false,error}`，错误退出非零。主要 action：snapshot、capture_start、capture_policy、launch、register_container、register_compose、start/stop/restart/force、project_policy、service_keep、end_project、codex_exit、history、logs、discover、cleanup、watcher_event。

配套入口的启动保存 argv 数组，不通过拼接 shell 命令执行；GUI 手工输入命令仅由 shlex 分词，需要 shell 语义时明确使用 shell argv。

## 界面设计

视觉主张：macOS 原生浅深色自适应，蓝色操作强调，紧凑可读的分栏工作区。
内容：左侧项目导航、中间服务/搜索/状态筛选、右侧配置/日志/历史；菜单栏为快速操作。
交互：选择详情过渡、操作状态反馈、系统 sheet 配置。尊重减少动态效果设置。

状态辨识采用共享 StatusAppearance 映射系统语义色与 SF Symbols，SwiftUI StatusBadge 提供图标、文字、浅色填充与边框。徽标使用独立自适应底色，选中行仍保留状态色；健康徽标显式加“健康”前缀。菜单栏每项使用相同映射的非模板彩色图标。状态标识不改变后端模型或控制链。

状态筛选复用现有 Picker，提供全部、运行中、未运行、处理中和需关注。列表用同一投影显示简化徽标，详情和历史保留原始状态。运行中的服务若有健康异常或诊断问题，也匹配需关注。筛选与项目和搜索相交，运行数量仍按原始运行中状态统计。

ProjectStatus 从完整项目服务快照汇总主状态、运行数量、总数和需关注数量；服务筛选和项目汇总复用 needsAttention。ProjectRow 的 Equatable 比较包含状态摘要，状态改变时刷新行而摘要未变时保留菜单稳定性。项目行保留名称/目录，另显示状态和服务数量，需关注另起一行以适应侧栏宽度。

## 构建与测试

用 `swiftc` 链接 SwiftUI/AppKit，脚本生成 Info.plist 并复制后端到 app Resources，ad-hoc codesign；无需完整 Xcode。Python 单元测试涵盖策略/身份/去重，独立状态目录实际集成测试验证进程树、真实启动链、Docker 和失败情况。GUI 用原生自动化验证实际可操作流程。

实际 Codex 退出由用户执行，独立 `tests/record_codex_quit.py` 经 `scripts/csm --task` 登记后观察原 Codex PID/出生身份消失、正式观察器产生的 codex_exit 操作、四项应停止服务及两项保留服务。记录程序不调用 codex_exit，不控制 Codex 界面。窗口关闭和菜单栏可见性需要实际界面证据或明确标注的人工观察；进程结果不能替代窗口证据。

最终采用自动原生 UI 与人工真实桌面操作共同验收：28 项原生断言、用户确认菜单栏详情/关闭 Codex 窗口、独立实际退出记录。测试结束后按精确 service ID、容器标签、Compose 项目和卷标签清理，测试历史先归档，再移除本轮登记以免留下不存在容器的异常项；保留正式观察器及原有服务记录。

## 开源交付方案

在独立公开快照中实施，不迁移私有 Git 对象。测试 support 模块统一创建 ignored 工作目录并解析工具；真实项目默认使用唯一测试状态。应用继续使用系统 Python，不打包运行时。CI 使用只读权限与固定官方 checkout 提交，不上传原始证据。Docker 用独立临时 runner；真实窗口截图仅测试数据，经人工查看和 SHA-256 白名单后发布。依赖只供测试安装，源码发行包不包含 node_modules、JAR 或系统框架。首版采用 GitHub prerelease 自动生成源码归档，构建安装包/签名/公证留待二进制分发。

0.2.0 准备：scripts/build.sh 的 CFBundleShortVersionString/CFBundleVersion 更新为 0.2.0/2，与 README、CHANGELOG 同步。重新构建并读取生成的 Info.plist、核验签名、文档链接与 Git 索引隐私；正常提交推送后新建 base=main 的 PR，按分支实际差异描述自动观察、接管及状态更新。GitHub PR CI 与既有本机验收分别记录；标签和 Release 发布另行执行。

用户授权发布后，从已合并 main 同步发布文档，核对版本、索引隐私和 main CI。通过后创建 v0.2.0 注解标签（noreply tagger），仅推送该标签；gh release 使用 --verify-tag 和 --prerelease，正文说明变更、安装、实测及缺口。核对远端标签解析提交、Release 非草稿/预览属性、源码归档链接和附件为空。

## 项目管理实现

使用现有 projects.name，无 schema 迁移。新增 project_rename、project_delete_preview、project_delete RPC；变更持有全局 mutation_lock，删除重新 observe 归属服务并在单个 SQLite 事务归档至 metadata 回收记录后移出关联表，不执行信号、Docker rm 或磁盘项目清理。只读快照容忍并发删除的服务行消失。CLI 增加 rename-project/delete-project（显式确认）便于诊断。SwiftUI 项目菜单打开改名/删除 sheet；删除 sheet 展示范围、数量、阻碍和重新检查，最终请求仍以后端为准。Store 在刷新后校正选择，并丢弃变更前已发出的旧快照。

复用 metadata 的 deleted_project:UUID 命名空间，无 schema 迁移；快照仅暴露名称/目录/时间/数量摘要。恢复校验目录和标识冲突并事务回填，随后移除归档。界面提供撤销删除和设置中的恢复列表。项目行使用 Equatable 避免刷新使上下文菜单收起，补齐标准编辑菜单。

## 审查修复设计（2026-10-27）

SQLite 建表及私有文件操作集中至 backend/storage.py，显式历史清理集中至 backend/maintenance.py；engine 保留共享 ROOT 与 RPC，capture 通过 metadata 保存禁用目录和脱敏诊断，无 schema 迁移。Swift 拆为 Models、Status、Store、Infrastructure 与视图/显式 @main 入口，构建脚本逐项编译和复制新增模块。

监督器取消主进程存活且无停止请求时的全进程组扫描，停止与退出路径继续实时查组。该阶段保留两秒 UI 轮询与单次 JSON RPC。详细范围见 [修复设计](../../docs/features/review-hardening/DESIGN.md) 和 [实施计划](../../docs/features/review-hardening/PLAN.md)。

后续空闲优化保留单次 JSON RPC。主窗口可见时约每 2 秒刷新，关闭、最小化或隐藏后约每 10 秒刷新菜单栏，重开即请求刷新。快照用一次联表查询读取暂停服务的登记和缓存。采集器保留一个无活动事务的 SQLite 连接，按目录变化重读事件文件，并在跟踪结果变化时才获取写锁和持久化。心跳约每 5 秒更新，错误变化时提前更新。复验见 [空闲资源回归](../../docs/TESTING.md#空闲资源回归)。

快照解耦后，界面定时读取和后台自动探测分别执行。应用通过长连接读取 SQLite 缓存，观察器、CLI 与显式操作继续使用单次 JSON RPC。后台按到期时间及项目策略执行有界探测，并复用项目代际和运行身份校验。验收使用 [260 条登记的同负载对照](../../docs/TESTING.md#快照性能基线)。

## P0 · 快照重复扫描修复

在 CachedSnapshotConnection.readLine 内记录已扫描字节数，只对新增区域用 memchr 搜索换行；使用 Data.startIndex 换算索引，保留下一帧剩余数据。每次 readLine 从剩余数据起点开始，连接 reset 沿用清空缓冲。仅修改读取热路径，不纳入后台探测、历史分页或 SwiftUI 状态重构。

对实际生产类编译 Swift 管道测试，覆盖分片、多帧、UTF-8、大帧、EOF、超时、上限及重连。使用同一隔离固定数据、同一编译优化参数和原生窗口，交替运行旧/新版本，预热后记录 CPU 与刷新延迟；运行引擎与缓存快照回归。测试前后核验全局采集器、hooks 和 62 个关闭目录。验收后按 self 系列约定本地提交，不推送或部署。

## P1–P3 交付顺序

用户后续授权 P0 上线并继续全部优化阶段。P0 正式窗口已替换，实际 CPU 4.57%，后台 11.17%，业务进程与容器身份未变。

1. P1：提取可测的快照应用入口，按业务字段差异发布。检查时间与加载状态使用独立 ObservableObject，仅更新消费它们的小视图。服务集合变化时更新 ID 索引、项目汇总和筛选投影，筛选输入变化只重算筛选。
2. P2：版本化摘要请求及按需详情，保留旧全量接口。摘要含展示、控制能力、新鲜度和运行版本；选择、运行或配置变化时读取详情并拒绝迟到响应。内容版本覆盖配置、投影、登记时间和观察策略，界面比较版本与新鲜度，避免重复桥接完整字典。菜单模式保留全局统计，恢复窗口重新读取全列表。
3. P3：持久到期索引或等效有界查询，在配置、运行、项目策略与观察结果变化时维护，最终仍核验代际和身份。历史事件复用已解析内容，文件删除、替换与变化均须失效。

P3 实施采用附加 `observation_schedule` 表及可见/隐藏到期索引，由 SQLite 触发器在服务、运行、项目策略和观察结果改变时更新；保持数据库 user_version=1，让已加载旧代码的业务监督器继续正常写入。按到期索引筛选、保留项目/变更/活动优先级，再限额 12 条读取配置。原来的共享观察锁、并发上限、最终代际与运行身份复核不变。历史事件按 inode/大小/时间/权限指纹复用；确认根身份已结束、没有保留的跟踪后代且 Docker 窗口已过的事件退出热集合，文件和历史不删除，文件变化或持久跟踪引用会重新纳入。

每阶段独立回归、自审和本地提交。保留相邻阶段完整源码/后端，固定同负载比较：1000 条数据重复测量 CPU，260/5000 条及大记录核验规模和体积，覆盖窗口与菜单。明确记录每轮时长，不把短试跑称作长期证据。正式采集器不启用。

## P4 · 启用采集后的优化方案

后续用户授权仅开启当前项目的 hooks/采集器。只读诊断确认每轮 925 条历史登记产生 1,851 个 SQLite 连接、约 583 ms CPU，却无有效本地运行候选。先实施候选预筛选和批量读取，再按剩余剖析决定同轮读取/进程探测复用，最后完成相邻版本的全链路启用对照。保留最终写锁内的新鲜校验；只读上下文限定线程与事务生命周期，不用于破坏性控制授权。

方案、证据限制、工程目标和回归矩阵见 [P4 诊断与方案](../../docs/results/CAPTURE_ENABLED_DIAGNOSIS.md)。诊断里程碑已本地提交；用户随后授权实施 P4-01。正式采集器保持开启、其他 61 个目录关闭，不替换应用或控制业务服务。

P4-01 使用一次联表读取候选，最新运行子查询与 engine.latest 排序一致；仅解码运行中本地候选的 runtime，再按跟踪 PID/事件过滤后解码 spec。无有效跟踪时不执行候选查询。读连接在外部探测前显式关闭，写锁内的策略/服务/运行复核不变，无 schema 变更。新增隔离契约与真实采集/进程回归；相邻版本真实 collect 循环采用 1,000 条合成终态历史、零活动/持续活动检查点，三组交替顺序 AB/BA/AB，各轮空闲 15 秒、活动 60 秒。这个 P4-01 对照不代替 P4-03 的完整 120 秒、多活动候选与窗口/菜单矩阵。

实施验收后，用户另行授权正式部署：核验构建、暂存并签名检查应用副本，按 csm 服务身份停止管理器后备份并替换应用，再启动管理器；持有 capture-start.lock 正常重启采集器，避免 hooks 并发恢复产生重复运行。停止失败不得继续启动。保持业务服务及项目开关，核验原业务身份、仅管理组件控制日志、实际窗口、新组件单实例和心跳；预热后使用与部署前相同的 60 秒 CPU/温度测量方法。此阶段已完成，结果见 P4-01 验收的正式部署章节。

### CI 夹具入口锁争用修复

`test_14` 创建无关项目时可撞上后台短写锁，原 `dispatch` 的零等待按契约返回 `MutationBusy`。测试辅助函数仅在当前进程的夹具调用期间替换锁入口并设置有限等待，随后恢复原函数；子进程采集器不受影响。这样等待只发生在执行前，不通过重复 dispatch 引入重复启动或重试部分完成动作。加入独立进程持锁、持续忙锁、入口后 busy 及其他错误四项回归，并保留真实 core 套件验收。
