# 后台观察优化设计

本文记录 P4-04～06 的架构、契约与验收条件。问题与测量基线见 [P4-D2 诊断记录](../../docs/results/WORKER_P4_04_DESIGN.md)，需求见 [主规格](spec.md)，结果见 [验收索引](acceptance.md)。

## 职责与状态归属

| 位置 | 目标职责 | 允许共享的内容与生命周期 |
|---|---|---|
| observation.observe_due | 在 observation.lock 内选择最多 12 个到期服务，编排分组和最多 6 个执行线程，收集结果后逐服务完成 | 一批候选与不可变探测结果；批次结束释放 |
| engine Docker 只读适配 | 构造保持原执行语义的命令、解析逐对象结果、验证 Compose 归属，不写业务状态 | 同批对象结果；禁止传入 start/stop/restart 等控制入口 |
| engine prepare/check/finish | 捕获服务/运行/策略版本，最终检查并生成运行与观察投影 | SQLite 为登记和历史权威；Docker 为外部实际状态来源 |
| engine/storage 连接上下文 | 批次内按线程建立读连接，协调线程拥有写连接；负责关闭、回滚与根隔离 | 连接不跨线程、不跨 ROOT 或数据库文件身份，不缓存 SELECT 结果 |
| snapshot_cached / observation.serve | 同一数据库读事务内生成协议响应，serve 拥有可丢弃摘要缓存 | 单 worker 内存缓存；不写数据库，不跨进程，不用于控制 |
| Swift Store/Infrastructure | 消费原有协议、处理迟到详情和 UI 刷新 | 不新增前端状态来源或刷新定时器 |

继续使用现有进程边界；不引入常驻 Docker events 订阅、HTTP Docker SDK、数据库连接池服务或额外 writer 线程。避免扩大部署和凭据边界。`engine` 的共享读工具保持兼容，批量适配仅从后台调用；显式 observe/手动刷新与控制仍可走原路径。

## D-04 · 逐对象批量结果

内部结果概念字段为 `service_version/run_version/policy_token`、`started/checked_at`、`objects_by_id`、`errors_by_id` 和 `members_to_ids`。不成为公共 RPC 或落盘格式。完成时复核完整服务/最新运行内容及项目创建/策略代际，并沿用 started 与较新缓存时间比较；不能只比较 config_revision。

执行顺序：捕获本批候选版本 → 不持有数据库事务地按等价调用配置分组 → Compose 成员发现 → 合并 inspect → 按服务组装结果 → 最终复核和持久化。独立组的超时不抹除其他已完成结果。同批外部读操作共享 4 秒单调时钟预算；Compose 发现阶段最多使用前 2.5 秒，为健康组的 inspect 和必要清单补查预留时间。所有查询共享同一个时钟截止点，最多 6 个执行槽，不因排队或补查重置。该分段使超时的 Compose 发现不能耗尽其他组的 inspect 预算；极慢或排队过久的发现保持 unknown，按现有节奏重试。

分组必须保持现有调用语义：`containers_for` 的 Compose ps 使用 runtime_env(spec)/cwd，而随后 inspect 当前使用 docker 默认调用环境，不能借优化擅自给 inspect 改用 Compose 环境。只有可证明执行上下文等价的请求才合并，显式 env/env_unset 差异保守分组；环境内容仅按现有命令调用传递，不写诊断、缓存键日志或响应。无法证明等价时分组隔离，不声称仍能合成一次命令。

Compose 发现结果须保留 ID→成员的最小映射，正常空成员和查询失败严格区分；优先使用最小格式输出而非包含 Command/环境的完整 JSON。实际支持的格式在 V-01 验证。inspect 对容器类型查询，保留返回 ID 与要求 ID 的严格对应；有效 JSON、必要状态字段和标签均通过才算可用。不接受前缀碰撞、重复冲突对象或其他 Docker 对象类型作为容器。

| 内部结果 | 对服务的外部行为 |
|---|---|
| 容器存在且字段/身份有效 | 正常计算状态、健康、能力及运行历史 |
| 独立容器 ID 确认缺失 | 维持 unknown 与问题说明，objects=None；不把空列表交给运行协调器结束历史 |
| Compose 发现成功且某成员无容器 | 允许该成员的空对象列表，沿用现有空成员协调语义 |
| Compose 已发现 ID 但 inspect 缺失/无效 | 该成员 unknown，不以残缺对象列表结束或重建运行；其他有完整映射、完整结果的成员继续成功 |
| daemon 错误、超时、无效/不完整输出 | 受影响项 unknown；不把失败解释成缺失，不修改其运行历史 |

非零退出时逐行保留可验证的有效对象；未返回对象最多用同调用上下文的一次成功清单查询确认缺失，不解析本地化 stderr 作为唯一缺失依据。清单成功也不能让“清单存在但 inspect 没返回”的对象变成正常；保持 unknown。Compose 成员映射不能验证时整个受影响 Compose 组失败，其他组和独立容器不受影响。诊断只保留现有脱敏问题语义，不发布完整 stdout/stderr。

正常调用数上限以实际等价组计：每组发现至多一次，每 inspect 上下文至多一次；只有确需分片的参数/输出容量限制可增加有界分片，验收须单列，不能以“分片”恢复每 ID 命令。发生版本变化时丢弃结果、保持待重新检查；不在同批循环单项重试。候选数不等于容器数，Compose 多副本、字段异常和大输出必须覆盖，沿用或收紧已有超时/协议边界，不加载 Env/健康日志。

V-01：在隔离注册表和自有 Docker/Compose 资源中记录客户端/Compose 版本，验证“有效+缺失+全部缺失”、最小成员映射、多副本、成功空成员、错误返回、模板字段缺省和 ID 对应。通过标准是在既定预算和命令边界内可靠区分完整结果与失败，并保留正常邻项。部分输出或映射无法可靠取得时，重新评估成功清单预筛选、批量 inspect 和命令预算。首次通过的记录见 [P4-04 验收](../../docs/results/WORKER_P4_04.md)。

## D-05 · 批次拥有连接，单服务事务写回

采用批次生命周期而非无限期线程池。准备阶段按执行线程复用一个 query-only、自动提交的读上下文；同线程处理多个候选，嵌套 prepare 复用已有上下文。协调线程按批次拥有一个写连接；缓存快照连接仍由 serve 线程独立拥有。这样连接数量随执行线程而非逐服务增长，代价是下一批仍需打开连接，但不增加常驻线程与长期事务管理。

写路径显式传递内部 db 参数至最终 check、运行协调和 persist；普通 CLI 调用保留默认自行开关连接的兼容入口。不能让已有 query-only 线程局部上下文截获写事务内的最新读取，也不能使 new_run/set_run 隐式另开连接提交一半结果。

对可能改变运行的结果，锁顺序固定为现有 mutation_lock → 每服务 reconcile 锁 → BEGIN IMMEDIATE → 最终复核 → 运行变化与投影写入 → 提交 → 释放。只改缓存的路径继续 BEGIN IMMEDIATE 内复核和写入，无须增加 mutation_lock。禁止已持有 SQLite 写事务再等待应用锁；显式控制保留原有身份核验与锁规则。监督器不依赖 mutation_lock，其更新必须被事务中的版本复核识别。

同一服务一次提交：失败全部回滚；其他服务已提交结果不撤销。遇现有忙锁语义则保留旧缓存，后续调度重试；不得在锁内执行 Docker、网络或睡眠重试。提交失败不返回 state_fresh=True，不推进 checked_at。异常/批次完成显式 close；文件身份/ROOT 改变时终止上下文并重新初始化，不能沿旧文件继续写。

去重只比较将写入的实际字段，runtime 按结构语义比较；不省略新的 started_at、ID、退出码、结束时间、健康/错误等变化。无变化时跳过 runs UPDATE，但仍推进观察 checked_at 并触发既有截止时间维护。不得用缓存相同为理由压掉真实新运行或重写历史 started/ended。验收须覆盖写到一半的异常、监督器竞争、删除/恢复同 ID 和跨 ROOT 嵌套。

Python 实际解释器 3.9.6、SQLite 3.43.2（本次只读版本检查），构建目标 macOS 13+、Swift 5。不使用仅新 Python 才有的 autocommit API；沿用 isolation_level 和显式事务，保留默认线程归属检查。连接上下文负责事务而不会自动 close，因此关闭由明确的 finally/closing 保证。依据 [Python 3.9 sqlite3 官方契约](https://docs.python.org/3.9/library/sqlite3.html)（2026-11-15 核对），不把此版本检查当作所有 macOS 环境兼容证明。

## D-06 · 精确内容失效，动态时间独立计算

每次响应仍在一个 SQLite 读事务内取登记、观察和元数据，先生成所有服务的最小统计/排序信息，再按现有 `running 优先、created_at 降序、id` 顺序选菜单前 16 条。不能在 SNAPSHOT_ROWS 的按 name 排序结果上先 LIMIT 16。项目侧栏、总数、健康/需关注、has_cached/has_paused 均覆盖全部适用服务；menu 项目列表仍按现有返回条目过滤。

缓存由 serve 持有并显式传入 snapshot_cached；独立 CLI 和 full 格式保留无缓存兼容路径。以状态根/数据库文件身份、服务 ID 和 detail_revision 所有输入字段的精确原值比较判断内容变化，不以 checked_at 或 PRAGMA data_version 充当内容版本。不变才复用解析后稳定内容和原 detail_revision；改变则按既有算法重新生成，保持迟到详情校验兼容。

每次生成新响应对象，重新叠加 checked_at、now、visible、paused、state_fresh/cache_state；不修改共享缓存对象，也不缓存最终 JSON。窗口模式切换、时间越过过期阈值、组件心跳失效、项目重命名/排序/删除等元数据变化即使服务内容未变也应体现在当前响应。删除服务条目及时淘汰，删除后恢复同 ID 重新核对全部版本。

不跨进程共享，不持久化，不用长 TTL 掩盖失效。工程容量上限暂定 5,000 项且估计驻留字节 16 MiB，先到者触发 LRU 淘汰；单项超限跳过缓存并正常计算，冷启动或淘汰只影响成本。该上限基于既有 5,000 条规模测试作为可调实现参数，不是实测内存承诺；估算须覆盖原值、解码对象和摘要，另测 RSS。ROOT/数据库文件身份变化、重连或格式不兼容时清空。无需新增 schema 或定时清理任务。

## 运行、兼容与回退

三阶段沿用数据库 schema、SQL view/触发器和 RPC 版本；内存缓存丢弃即可恢复，不迁移生产数据。测试同时覆盖旧 full、新 list/menu 调用者及旧进程并存写入；显式控制不得依赖新缓存存在。实现后先独立状态回归与匹配 CPU 对照，再按单独部署授权替换应用和管理组件，不操作业务服务。回退只替换程序、重建内存上下文，不能回滚用户最新登记或运行历史。

选型取舍：Docker CLI 合并优于引入 SDK/长订阅，因为能沿用当前调用和部署边界；批次连接优于常驻连接池，因为足以先消除条目级重复且退出生命周期明确；精确内容比较优于纯 TTL/每次全量哈希，因为保持动态新鲜度且不引入持久版本迁移。实际收益是待测结论，若无稳定改善应缩小或撤回相应优化，不扩大技术栈。

W-04 对每场景保留原始分段和配对结果；测试时间内业务主动变化单独记录，不伪造相同负载。必要功能/一致性场景失败为 FAIL；关键验证没运行标 NOT_RUN。未设定数值的性能代价不得隐去：三组效果不稳定、资源或延迟恶化时标 WARN 并说明，部署不在这份设计的默认授权内。

负载应复现约 1,035 条记录，其中 40 个确认缺失 ID、8 个停止/失败容器记录、5 个 Compose 成员/2 组，其余普通终态历史；采用隔离注册表和测试自有资源生成，不通过停止或删除真实业务来制造负载。活动场景另加自有容器，保留外部恢复探测。沿用现有引擎/观察/采集回归及真实 Docker/Compose 入口，变更服务模型时运行相关真实集成测试；影响 UI 时重新构建并核验实际窗口。

性能需在三组匹配场景中证明总 CPU 下降，并同时说明命令计数、延迟和资源代价；未稳定改善则保留 WARN 并继续归因。28.08% 为现场基线，不能与另一负载孤立测量相减充当收益。不预先承诺剩余 CPU 全部消失，也不把此前未达成的整体 80% 目标改写为已完成。
