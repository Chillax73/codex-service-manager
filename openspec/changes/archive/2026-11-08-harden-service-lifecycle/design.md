# Design

## Context

现有引擎把运行、操作和回收档案保存在同一 SQLite 状态目录。自动采集和配套登记入口共用该库，退出观察器独立于主窗口，现有日志清理只识别有效运行 ID 对应的本机路径。详见 [提案](proposal.md)。

## Goals / Non-Goals

**Goals**

- 用同一身份规则匹配候选容器和现有登记。
- 让启动失败、退出策略结果及回收操作都能通过现有操作入口核验。
- 兼容已有状态库、运行历史与 `deleted_service:*` 记录。

**Non-Goals**

- 进程信号、退出触发、项目结束策略和项目回收流程沿用现行契约。
- 快照探测和界面 RPC 优化由独立变更处理。

## Decisions

### 按容器身份和 Compose 归属去重

优先匹配完整容器 ID，保留既有归属。仅对正式 Compose 成员登记执行第二层匹配，要求项目名、服务名以及规范化配置来源可核验。匹配时复用已有 Compose 归属校验使用的路径规则，候选缺少必要标签时不把缺值当作匹配。全程保留项目扫描策略与提交时的代际检查。

只给原比较加非空判断能修复普通容器漏记，却无法区分同名 Compose 配置。因此将完整 ID 和 Compose 成员匹配拆开。

### 以监督进程是否已创建划分启动失败

记录运行后，将打开日志与创建监督进程的错误收敛在明确的创建前边界。确认未创建进程时，只将本次仍处于启动中的运行写为已结束失败，沿用启动配置回滚和脱敏逻辑。一旦创建成功，确认超时、监督进程提前退出且业务子进程状态未明等情况走现有身份保护，并验证正常完成的监督进程结果不会被旧写入覆盖。

旧版遗留空记录可能跨越不同失败阶段，继续展示诊断并保留身份保护。根据空字段自动批量结束旧记录会引入重复启动风险。

### 保存批次结果，保持心跳独立

复用 `codex_exit` 已返回的项目和服务结果，为最近一次事件保存时间、执行状态、成功、跳过、失败计数和脱敏失败摘要。已执行结果由后端在批次结束时持久化，现有调用方仍能读取逐项目结果。观察器捕获始终未能提交或结果无法确认的情况，和已执行批次的部分失败分别展示。

心跳更新与批次执行分开，心跳写入也不能覆盖已保存的最近结果。只在能确认批次尚未开始的锁忙场景重试。通过抛异常表达任意单项失败会丢失已成功和跳过的信息，也容易让调用方误重放批次。

### 沿用单服务归档，增加可恢复和可重试清理的状态

沿用现有归档键及载荷，缺少清理标记的记录按可恢复处理。清单只投影名称、原项目、日期、数量和状态。恢复在一个事务内校验项目、服务 ID 和已知容器归属冲突，写回原登记、历史和操作，再移除对应归档；保留既有配置的脱敏边界。

按 `deleted_at` 预览并确认待清理归档，提交时重新校验候选。先在 SQLite 中标记进入清理，随后仅移除归档运行 ID 对应、路径和文件类型可核验且未被其他记录引用的日志及轮转文件，最后移除归档记录。文件不存在可视为已清理，I/O 失败保留清理状态以便重试。普通历史清理和项目归档保持原有入口和保留规则。直接把归档并入普通历史清理会让原有按钮额外产生永久删除。

## Risks / Trade-offs

- Compose 标签不全 → 需要可信来源才能建立归属，拒绝把同名当作归属证明。
- 批次完成但 RPC 响应丢失 → 以已持久化结果为准，缺少证据时展示结果未确认。
- 清理与恢复或重新登记并发 → 同一写入约束下校验冲突及日志引用，清理中的归档不可恢复，失败可续做。
- 损坏或无法核验的归档数据 → 限定失败在单条记录内并提供诊断，保留外部文件与其他有效记录。

## Migration Plan

新增状态以可选元数据或可选归档字段保存。旧数据由原结构读取，升级时不清理历史或修正旧进程记录。回退前先完成已开始的归档清理，保留状态目录及数据库备份。常规 CI 使用隔离数据库和替身测试，真实 Docker 与 Codex 退出用独立夹具复验。
