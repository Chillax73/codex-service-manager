# Design

## Context

`Store.refresh` 目前把定时读取和显式刷新送入同一 Swift RPC 入口，每次启动独立 Python。引擎 `snapshot` 对开启项目执行探测，SQLite 已有 `service_observations` 和项目观察代际。采集器另有已观察服务检查循环，CLI 列表和发现也在调用现有快照。详见 [提案](proposal.md)。

## Goals / Non-Goals

**Goals**

- 在应用运行期间复用读取连接，避免定时读取创建 Python 或等待外部探测。
- 让同一状态目录的到期自动探测共用调度规则，复用现有缓存、代际和操作核验。
- 将界面呈现、状态更新延迟和全链路资源开销分开度量。

**Non-Goals**

- 继续使用本机 SQLite 和当前工作目录归属。网络监听、开机自启、hooks 信任及外部服务生命周期不属于本设计。
- 退出观察器、CLI 和显式操作沿用一次性 RPC 协议。项目暂停和手动刷新保留各自权限及范围。

## Decisions

### 为周期快照提供只读路径

在引擎增加专用缓存快照请求，批量联表读取服务、项目、缓存和必要元数据，保留现有排序、筛选、脱敏和摘要字段。周期请求不触发观察、探测组件 PID 或持久化状态。组件存活提示从后台核验结果和心跳时效派生。缺少观测或已过期时使用明确的缓存状态，检查时间取自真实观察。

显式 `refresh`、CLI 列表和发现先维持现行入口与语义。逐个迁移所有调用方会改变 CLI 的即查即用行为，也会让性能比较混入无关变化。

### 应用复用仅服务读取和调度的本地 Python 子进程

由 Swift 管理一个应用期内的子进程，使用标准输入输出分帧的 JSON 请求；窗口关闭但应用留在菜单栏时继续复用。子进程内将快照读取与耗时探测放在不同执行队列。读取连续失败时保留最近成功画面并标过期，按有界退避重连。应用退出后该子进程随连接结束，采集器和退出观察器延续原生命周期。

直接从 Swift 查询 SQLite 会把状态投影、兼容性和脱敏规则复制到界面。让所有显式操作共用一个串行连接则会让缓慢的 Docker 操作阻塞定时读取，因此显式操作继续走独立的一次性请求。

### 共用后台探测调度，显式检查独立

应用的状态子进程与现有采集器使用同一个 Python 调度入口。以状态目录的专用互斥锁协调短批次，在锁内重新筛选到期项，按最近实际检查时间、服务状态、窗口可见性及优先刷新请求调度。仅采集器运行时延续其原有的已观察服务范围。采集器将周期检查提交给独立的有界执行队列，shell 检查点及发现归属仍由原采集循环处理；发现流程可以提交已核验结果供状态层复用。每轮只领取有限工作，未取得锁的后台调用跳过本轮并退避。对 Docker 等慢探测设置超时和失败退避，单项结果完成后即可提交。

每次后台探测都沿用项目观察代际、服务配置及运行记录校验；暂停、删除、重新登记或更新先发生时丢弃旧结果。显式刷新按范围直接实时检查，不排在普通背景任务之后。启停和删除沿用实时身份核验，避免用缓存决定能否操作。

### 分开设置显示节奏和探测时效

窗口可见和菜单栏驻留继续约 2 秒和 10 秒读快照。重开先显示缓存，再优先调度到期服务。先以正在运行或过渡的本机服务优先、空闲或较昂贵的探测降频为默认策略，并对连续失败退避。通过实测选定分类型时效预算，纳入实现和文档。缓存读到新运行时合并更新详情，避免同一代状态反复拉取历史和日志。

## Risks / Trade-offs

- 全部探测移到后台但总开销未降 → 计入窗口进程、Python、探测子进程、观察器和采集器，分别核对 CPU、写入及进程数。
- 慢 Docker 检查拖住健康状态更新 → 限制单轮工作量和并发，避免外部命令占住缓存读取队列、采集循环和全局操作锁。
- 暂停后旧结果覆盖缓存或后台故障显示正常 → 沿用提交校验，区分后台故障、过期和探测错误，测试断连和重连。
- 新旧组件共享状态目录时可能重复探测 → 使用现有同版本升级步骤；回退时退出新状态子进程并使用旧版应用和采集器一起运行。

## Migration Plan

复用现有状态缓存。首次启动时可直接读取兼容的旧投影，缺失或过旧的项等待后台探测。优先增加缓存请求和调度，再切换 Swift 周期路径。验收在相同机器、相同版本对照方式和相同 260 条夹具数据下重复采样，分别记录窗口打开、菜单栏驻留和仅后台运行的总资源，以及外部进程退出、容器状态和健康变化到界面可见的延迟。发布前记录实测预算，并确认收益高于基线重复采样的波动。
