# Spec Delta

## Purpose

让用户直接管理服务显示名称、适用类型的启动参数和健康检查地址，并在确认已停止后删除登记。所有修改应保留稳定身份及当前运行的可核验性，删除不形成永久屏蔽，也不把配置保存误当成启停操作。

## ADDED Requirements

### Requirement: 服务改名保持身份且不被采集覆盖
系统 SHALL 允许修改服务显示名称并保留服务标识、所属项目、创建时间、配置和运行历史。用户自定义名称优先于自动生成名称，后续自动采集及重复登记不得覆盖它。

#### Scenario: 运行中改名
- **WHEN** 用户修改运行服务的显示名称并成功保存
- **THEN** 新名称立即展示，原运行与稳定标识保持不变，不发生启停

#### Scenario: 自动采集再次报告名称
- **WHEN** 用户改名后采集器更新相同服务的端口、名称或状态
- **THEN** 用户自定义名称继续展示，采集信息仍更新到同一服务

#### Scenario: 名称无效
- **WHEN** 用户提交纯空白、超过 100 字符或含控制字符、不可见格式及换行的名称
- **THEN** 系统拒绝保存并说明原因，保留表单输入与已有登记

### Requirement: 按服务类型提供配置编辑
系统 SHALL 允许本机进程和后台任务编辑启动命令、工作目录、环境变量及健康检查地址；Docker 容器和 Compose 成员支持改名、删除及编辑健康检查地址，不开放需要重建容器的命令、目录和环境编辑。

#### Scenario: 编辑本机进程或后台任务
- **WHEN** 用户打开本机进程或任务的配置表单
- **THEN** 系统提供启动命令、工作目录、环境变量和健康地址的编辑入口，清楚展示保存用途

#### Scenario: 编辑 Docker 或 Compose 服务
- **WHEN** 用户打开 Docker 容器或 Compose 成员的配置表单
- **THEN** 系统允许编辑名称和健康地址，并提供符合删除条件的删除入口
- **AND** 容器启动命令、目录和环境参数保持只读，明确说明本版不包含容器重建

### Requirement: 配置保存对当前运行无副作用
系统 MUST 将编辑的启动和健康配置保存为下一次启动使用的配置；保存不启动、停止或重启服务，不改变当前运行的身份核验、停止范围、健康探测地址及运行记录。

#### Scenario: 运行期间保存新命令和健康地址
- **WHEN** 服务运行中，用户保存新启动命令、工作目录、环境或健康地址
- **THEN** 系统展示待下次启动生效的配置，当前运行仍按原配置检查和停止

#### Scenario: 下一次启动应用配置
- **WHEN** 用户显式启动已停止服务，或旧运行被核验停止后继续显式重启
- **THEN** 系统使用最新保存配置创建新运行并清除待生效提示，保留服务标识和创建时间

#### Scenario: 停止失败
- **WHEN** 用户请求重启但旧运行停止失败或身份无法确认
- **THEN** 系统不启动新副本，也不将待生效配置应用到旧运行

#### Scenario: 取消或保存失败
- **WHEN** 用户取消编辑，或校验和持久化失败
- **THEN** 现有配置、当前运行和历史保持不变，失败时说明原因并保留输入

### Requirement: 配置输入校验与私密环境保留
系统 MUST 在保存时校验单项命令、真实可用工作目录、合法环境键和可选 HTTP/HTTPS 健康地址；未编辑的环境值保留，明确删除的键才移除，不把已有环境值回传到常规快照、历史摘要或错误消息。

#### Scenario: 不完整命令或不存在目录
- **WHEN** 用户提供空命令、无效参数结构或不存在的工作目录
- **THEN** 系统拒绝整个配置保存，不留下部分生效的字段

#### Scenario: 保留未修改的环境
- **WHEN** 用户只修改命令或部分环境键，没有明确删除其他键
- **THEN** 系统保留其余已保存环境值，界面可显示键名但不回显旧值

#### Scenario: 显式删除环境键或清空健康地址
- **WHEN** 用户明确删除环境键或将健康地址清空并保存
- **THEN** 下一次启动配置不再包含该键，或不再配置该健康探测，当前运行配置仍不改变

#### Scenario: 健康地址无效
- **WHEN** 健康地址不是可解析的 HTTP/HTTPS 地址
- **THEN** 系统拒绝保存并定位错误，不用保存动作发起探测请求

### Requirement: 服务删除要求实时确认无活动运行
系统 MUST 在删除服务登记前实时核验，拒绝存在启动中、运行中、停止中、停止失败、未知状态或任何未结束运行的对象。用户必须先手动处理活动对象，删除动作本身不发送停止信号。

#### Scenario: 尝试删除运行或未知服务
- **WHEN** 用户删除请求对应服务经实时检查仍活动、停止失败、未知或有未结束运行
- **THEN** 系统拒绝删除并说明先手动停止或核对状态，服务登记及其历史不变

#### Scenario: 删除预览后服务状态变化
- **WHEN** 删除确认界面显示可删除，但最终提交前服务又启动或状态变得未知
- **THEN** 系统按提交时的实时状态拒绝删除，不依赖旧预览或暂停项目的缓存

#### Scenario: 已无活动对象的服务被确认删除
- **WHEN** 用户确认删除，且实时核验没有活动或未结束运行
- **THEN** 系统事务性移除当前登记及其当前列表关联记录，保留源码、容器、卷和本机日志
- **AND** 已留存的登记、历史与操作信息存入私密本机回收记录，失败时整体回滚

### Requirement: 删除登记不屏蔽后续自动采集
系统 MUST 不因删除服务创建忽略标记、黑名单或永久排除规则；当项目扫描开启且新的采集结果满足现有身份及归属条件时，系统允许服务重新登记。

#### Scenario: 删除后再次发现有效服务
- **WHEN** 某服务的登记已删除，且自动采集随后核验到符合登记条件的活动服务
- **THEN** 系统允许重新添加；新登记有新的创建时间，不将回收记录误合并成新运行历史

#### Scenario: 项目暂停期间删除
- **WHEN** 服务已删除但其项目自动扫描仍暂停
- **THEN** 系统不会仅为重新登记绕过项目开关；以后恢复扫描时仍可按正常条件添加

### Requirement: 原生入口与选择状态一致
系统 SHALL 在服务列表上下文菜单及详情中提供改名、配置和删除入口，并按类型及实时操作结果展示可用性；删除后清理失效选择，失败不清空用户输入。

#### Scenario: 删除当前选中服务
- **WHEN** 当前选中的服务被成功删除
- **THEN** 列表、数量和详情同步更新，不保留指向不存在服务的详情或操作目标

#### Scenario: 跨项目操作
- **WHEN** 用户编辑或删除项目甲的服务
- **THEN** 项目乙的服务配置、运行、扫描策略和历史保持不变
