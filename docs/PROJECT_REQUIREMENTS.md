# Codex Service Manager 项目需求文档

版本：0.3（已确认需求与实施基线）

日期：2026-10-13（Asia/Shanghai）

目标平台：macOS；使用对象：个人开发者。

当前阶段：原生应用与项目配套完整控制已完成本机 A-01 至 A-16 验收；开发分支新增用户级自动观察。新聊天常见 shell 路径已验证，普通启动接管的常见路径及显式配置已交付；旧聊天加载、后台发现兜底和任意复杂包装自动拆分仍待扩展。自动观察及项目管理增强未包含在 v0.1.0 标签。

## 1. 产品目标

集中展示 Codex Mac 桌面聊天启动的本机前端、后端、Docker/Compose 与后台任务，按项目或 worktree 查询运行状态、健康与历史，对具备可靠控制配置的服务提供启停和重启。

应用应回答：启动了什么、属于哪个项目、是否仍运行、是否可访问、哪些操作可用、失败原因是什么，以及项目结束时哪些服务应停止或继续运行。

“任意聊天启动后自动出现”是目标需求。逐项目 AGENTS.md 接入、配置文件中列出了 hooks，或某个新聊天测试成功，都不能单独证明该目标完成。

## 3. 功能范围与交付状态

| 编号 | 功能 | 要求与当前状态 |
|---|---|---|
| F-01 | 服务登记与归属 | 配套入口保存项目、身份和启动配置，已验收；用户级 hooks 自动观察新聊天常见启动路径，旧聊天覆盖未完成。 |
| F-02 | 状态与健康 | 区分实际运行、健康和组件不可用；彩色图标/文字徽标、十一种运行状态精确筛选、项目状态及独立需关注汇总已交付，观察对象纳入。 |
| F-03 | 单服务控制 | 已管理对象支持停止、启动、重启；任务支持取消/重新执行。观察对象按可靠身份/范围开放停止，常见命令或显式配置齐备后可启停/重启。 |
| F-04 | Docker/Compose | 已管理成员/组控制去重且逐项反馈；自动观察仅依据明确 ID 或启动配置与标签关联。 |
| F-05 | 项目结束策略 | 手动结束与退出 Codex 两个独立开关，服务保留例外优先；只作用于可确认的已管理对象。 |
| F-06 | 运行历史 | 每次运行独立 ID，保存可获取的起止、身份、结果和诊断；不伪造未采集的退出码和日志。 |
| F-07 | 操作结果 | 防重复操作，记录成功/失败/跳过；停止失败不得继续重启。 |
| F-08 | 持久化与恢复 | 重新打开核对实际状态；独立监督器、退出观察器和采集器分别展示能力及故障。 |
| F-09 | 项目管理 | 改名仅改显示；删除登记事务归档并支持撤销/恢复，不删除源码、容器、卷或日志。 |
| F-10 | 任意聊天覆盖 | 安装前已打开的旧聊天也应纳入，配置重载及无 hook 的发现兜底待实施验收。 |

原生主窗口、菜单栏、搜索、项目分组、日志/历史、批量操作、服务例外及发现页已实现。手动发现页不是全局后台自动登记兜底；项目配套完整控制验收不代表 F-10 完成。

远程服务器、账号/云同步、多用户协作、开机自启及安装前完整历史恢复不属于当前版本。v0.1.0 为源码开发者预览，未提供公证安装包；公开分发不改变上述能力边界。

## 4. 对象、身份与能力

| 对象 | 定义与身份 |
|---|---|
| 项目 | 以规范化 cwd 区分，同仓库不同 worktree 保持独立作用范围；显示名称可修改。 |
| 服务 | 使用稳定 ID；名称、PID、端口均不能单独作为身份。 |
| 运行 | 独立 UUID，关联服务；新运行不覆盖旧历史。 |
| 服务组 | 明确记录 Compose 项目/成员与控制范围，避免重复操作。 |

- **已管理**：具备明确归属、可靠身份与适合其类型的控制信息；能力仍按当前状态判断。
- **自动观察**：有启动关联和运行身份，可看状态与历史；按实际身份和单项范围分别提供手动控制能力；缺少配置时不能重启，原运行不参与项目结束策略。
- **发现候选**：只能发现对象，尚无可靠项目或 Codex 来源证据；不能直接当作自动观察/已管理对象。
- **暂时不可控制**：身份、Docker 引擎或监督器无法确认，显示未知与原因，不能按已停止处理。

自动观察不会接管业务进程的父子关系或输出，也不保证业务服务脱离原工具生命周期存活。常见命令自动保存必要配置或用户补齐单项配置后，可经管理器重启获得监督与新运行日志；配套入口仍提供直接完整控制。

## 5. 状态、控制与历史规则

运行状态与健康分别展示。TCP 监听不等于 HTTP 健康；Java 进程存在但健康失败时展示“运行中 / 不可用”。Docker 引擎不可连接时展示未知，不能统一报停止。

状态颜色保留文字和图标：绿色运行/成功/健康可用，红色已退出/已停止/失败/停止失败/健康不可用，橙色过渡/未知/需关注，灰色未运行/已取消/未配置。状态筛选逐项精确匹配，与项目及搜索相交；需关注单独汇总诊断问题、失败、停止失败、未知和健康不可用。项目状态统计全部所属服务，不随列表筛选变化；运行数量与异常提示可同时出现。具体汇总优先级见 spec，实际窗口验收见 [状态显示报告](results/STATUS_DISPLAY.md)。

启动先确认实际对象，再检查就绪；工具调用成功或聊天完成回复不能代替现场状态。重启先确认旧运行停止，再按原 cwd、argv 和必要环境启动，禁止意外副本。本机信号前核对 PID、出生身份及监督 token；身份不符拒绝操作。正常停止等待 5 秒，超时由用户明确选择强制停止；Docker 使用原生 5 秒 stop，保留容器和数据。

后台任务正常完成、失败、取消分别记录。自动观察进程无法获取退出码时保留空值，结束时间是观察时间，可能晚于实际退出；不根据消失推断成功、失败或取消。容器起止优先取实际 Docker 状态。项目/批量操作逐项记录并去重。

历史从采集开始积累，重新打开按真实身份核对。配套入口每次运行日志 1 MiB，保留 2 个滚动文件；历史默认不自动删除，清理只作用于已结束记录。自动观察不补回原本未采集的本机 stdout/stderr、完整环境或历史。

## 6. 项目结束与项目管理

手动结束默认开启，退出 Codex 默认关闭，两个开关独立；服务 keep 例外优先。结束工作是对指定项目的明确动作，回复结束、切换/归档聊天、关闭窗口都不是结束工作或应用退出。

退出 Codex 指目标桌面应用最后一个实例终止，由独立原生观察器处理；系统通知不能区分普通退出与强制退出，两者均触发，关机不保证操作完成。SessionEnd 不作为退出的唯一判断。退出管理应用保留服务、退出观察器及自动采集器。

重命名保留 cwd、身份、策略和历史。删除前后端重新确认不存在活动、停止失败、未知或未结束运行，事务归档登记和历史；撤销/恢复不启动服务，同目录或 ID 冲突拒绝覆盖。回收记录含原先保存配置，仅留本机；当前无永久清空或自动过期入口。删除项目不删除源码、容器/卷或日志，也不代表擦除敏感信息。

## 7. 用户级自动观察要求

一次安装用户级 PreToolUse/PostToolUse，经 Codex 正常信任审核后，在已加载配置的聊天采集启动 shell 身份与后代。独立采集器跟踪 PID+出生身份，监听进程分别展示，无端口叶子任务持续约 30 秒后显示。短暂非监听子进程不登记；与配套入口去重。

安装/移除保留其他 hooks 和指令，只修改本工具带标记条目；安装不授予信任。正常端口/进程审批需说明自动附加的采集检查点和本机元数据写入，不删除前缀或绕过信任/沙箱继续。定义变化后正常重新审核。

仅保存必要元数据：启动关联标识、cwd、进程身份、实际端口，以及指定容器身份/状态/Compose 标签。原始命令和必要 Docker 输出仅临时识别，不持久化；不读取聊天正文、完整环境、凭据文件或完整容器环境。数据留本机，目录 0700、文件按 umask 0077 创建。

观察对象控制在 UI 和后端按实际能力限制；手动批量按能力执行，项目结束策略仍跳过原运行，不能把未知对象冒充接管完成。没有可靠启动关联时不认领其他进程，仅凭端口新增、名称或启动时间不足以确定来源。

## 8. 当前覆盖与已知缺口

| 范围 | 结论 |
|---|---|
| 项目配套完整控制 | A-01 至 A-16 本机验收通过，含真实 Vite/Spring/Python、Docker/Compose 和真实 Codex 退出。 |
| 新聊天常见启动 | 一个无项目指令的新桌面聊天真实采集两个 HTTP 服务和一个任务；原生窗口显示正确项目与三个运行对象。 |
| 进程/Docker 采集集成 | 8 组真实进程和 6 项真实容器断言通过；这些集成测试的 hook 输入为模拟，区别于真实桌面回调证据。 |
| 旧聊天 | 已复现安装前旧聊天后续启动未产生采集事件；新窗口继续旧聊天没有解决。正常共享运行时重载未实施、未验收。 |
| 后台发现兜底 | 尚未实现；当前不事后补录启用前对象，配置检查和组件健康不代表所有聊天已接入。 |
| 复杂启动 | 采样前完全脱离已知父进程的脚本、复杂 shell 包装、脚本内部 Docker 可能漏记；控制/重启配置待补齐。 |
| 其他路径 | 远端与未触发 shell hooks 的执行路径不覆盖。 |

最近旧聊天诊断中，聊天声称运行的服务实际没有目标 TCP 监听且容器已退出；未伪造运行记录或重启业务服务。这只能说明检查当时状态，退出原因未确认。

当前可用路径是新建聊天加载已审核配置，或按项目配套入口登记所需服务；不应为了登记而重复启动已经运行的业务对象。尚无已验收的旧聊天热加载操作，不将重启 Codex 当作无副作用步骤（可能触发项目退出策略）。

## 10. 实施顺序与完成定义

已完成：统一管理模型与监督器、Docker/Compose、原生工作区/菜单栏、独立退出观察器、配套接入、原版真实验收、项目改名/删除/恢复，以及新聊天常见路径自动观察。

后续顺序：验证正常旧聊天配置加载 → 增加具备可信归属与独立来源的后台发现兜底 → 扩展复杂包装的自动拆分；普通启动接管的现有边界见独立报告。具体任务见 [tasks](../specs/001-service-manager/tasks.md)；设计见 [plan](../specs/001-service-manager/plan.md)，数据与接口见 [data-model](../specs/001-service-manager/data-model.md) 和 contracts.json。

旧聊天、多项目/worktree、未关联对象排除、已退出对象和复杂 Docker 路径应有真实验收。睡眠唤醒、系统重启恢复、Intel/其他 macOS 版本的完整桌面流程以及二进制签名/公证另行验证，不能由当前环境结果推导。

完成定义：目标环境中无需逐项目或逐次补填即可覆盖用户要求的聊天启动；状态、归属、历史和能力真实，项目策略作用对象正确，剩余限制有证据且明确披露。当前原版已交付，新增任意聊天目标仍有待办；文件存在、hooks 已信任或单个新聊天通过均不足以把全部目标标为完成。
