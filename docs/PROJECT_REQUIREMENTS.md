# Codex Service Manager 项目需求文档

版本：0.1（需求讨论稿）

日期：2026-10-12（Asia/Shanghai）

目标平台：macOS

使用对象：个人自用

当前阶段：需求整理与技术可行性验证，尚未实现完整 Mac 应用

## 1. 产品目标

提供一个随时可用的 Mac 服务管理应用，集中展示 Codex Mac 桌面应用启动的本机服务与后台任务，支持查看状态、停止、重启和查询运行历史。

应用需要回答以下问题：

1. Codex 启动了哪些服务，哪些还在运行？
2. 服务属于哪个项目或 worktree，使用什么端口和访问地址？
3. 服务进程仍在运行时，服务是否真的可以访问？
4. 如何停止或重启指定服务，以及如何查看操作失败的原因？
5. 项目结束工作时，哪些服务应该停止，哪些应继续运行？
6. 服务停止后，如何查看之前的运行记录？

## 3. 第一版范围与优先级

### 3.1 核心功能（P0）

| 编号 | 功能 | 要求 |
|---|---|---|
| F-01 | 服务登记与归属 | 通过配套接入入口记录服务身份、项目、启动配置和管理方式。支持多项目同时存在。 |
| F-02 | 当前状态 | 展示服务运行状态，并分别展示可获取的进程、端口和健康检查信息。 |
| F-03 | 单服务控制 | 支持本机服务和 Docker 容器停止、启动已保存服务、重启；后台任务支持取消和重新执行。 |
| F-04 | Compose 管理 | 识别服务组与成员，支持成员及整组控制，明确操作影响范围。 |
| F-05 | 项目结束策略 | 根据每个项目的设置，在手动结束工作或 Codex 真正退出时停止应停止的服务。 |
| F-06 | 运行历史 | 保存每次运行的开始时间、结束时间、结果与必要的诊断信息。 |
| F-07 | 操作结果 | 展示停止中、启动中、成功和失败；提供最近错误及可获取的日志。 |
| F-08 | 持久化与恢复 | 应用或管理界面重新打开后，恢复记录并重新核对实际状态。 |

其中，Codex 桌面登记、归属和真实退出检测是 P0 的交付验收条件。2026-10-12 已通过正式本机验收：登记/归属以项目配套入口为边界，实际 Codex 退出有独立观察器和持久化结果证据；详见 specs/001-service-manager/acceptance.md。以下原型阶段记录仍保留其历史覆盖边界。

### 3.2 建议的辅助功能（P1）

- 菜单栏快速查看异常、运行中的服务和常用操作。
- 主窗口按项目分组，支持搜索与状态筛选。
- 项目批量停止、批量重启，逐项展示结果。
- 服务访问地址一键打开或复制。
- 项目内设置某个服务持续运行的例外。
- 发现已有进程或容器，补充配置后接管。
- 日志滚动保存、历史清理设置。

菜单栏与主窗口作为建议的产品形态；具体布局和视觉设计在原型阶段确定。

### 3.3 当前范围之外

远程服务器与远程容器管理不属于当前版本。账号、云同步、多用户协作、公开分发与安装前完整历史恢复也不作为第一版交付目标；后者只能根据已有证据尝试导入，不能承诺完整恢复。

## 4. 概念与对象

### 4.1 项目、服务、运行记录

| 对象 | 含义 | 身份要求 |
|---|---|---|
| 项目 | 服务的管理与结束策略作用范围 | 建议按工作目录及 worktree 区分，同一仓库的不同 worktree 不混为同一操作范围。 |
| 服务 | 一项可重复启动或执行的定义 | 使用稳定 ID；名称、PID、端口都不能单独作为固定身份。 |
| 运行记录 | 某服务的一次实际运行 | 每次启动或重新执行生成独立 ID，关联同一服务。 |
| 服务组 | 多个关联服务，例如一个 Compose 项目 | 记录组身份、成员和控制范围，避免与成员重复执行同一操作。 |

例如，同一个 worktree 的前端昨天运行两次、今天运行一次，列表展示一个前端服务，历史展示三次运行。两个 worktree 中的同名前端作为不同服务实例管理。

### 4.2 接管能力

服务需要区分以下状态：

- **已管理**：身份与归属明确，具备适合其类型的控制信息，可启用相应操作。
- **已发现、未接管**：仅能可靠观察状态；补齐身份、启动配置和控制方式后接管。
- **暂时不可控制**：原来已管理，但进程身份、Docker 引擎或监督进程当前无法确认；显示原因，不把不确定状态当作正常。

操作能力按实际信息分别判断，例如能停止不一定能重启。自动结束策略只作用于明确归属、已接管且符合策略的服务。

## 5. 状态与操作规则

### 5.1 状态分层

| 层次 | 展示内容 |
|---|---|
| 运行状态 | 启动中、运行中、停止中、已停止、失败、状态未知；自然退出另记录退出结果。 |
| 健康状态 | 可用、不可用、检查中、未配置检查；与运行状态独立。 |
| 控制能力 | 当前是否可停止、启动或重启，以及不可操作的原因。 |

后台任务使用“执行中、成功、失败、已取消”等结果；正常完成不显示为服务异常。Docker 保留其原生状态与可获取的健康检查结果，再映射到统一展示。

状态示例：Java 进程存在但 HTTP 检查失败，应展示“运行中 / 不可用”；Docker 引擎不可连接，应展示“状态未知 / 引擎不可连接”，不能把所有容器显示成已停止。

### 5.2 启动与重启

- 保存执行方式、工作目录、必要的环境配置及健康检查配置。
- 服务启动后，先确认实际运行对象，再检查就绪状态；命令执行成功不等同服务可访问。
- 重启先停止旧运行，再按保存配置启动新运行；不能静默启动第二个副本。
- 如果停止失败，停止重启流程并展示原因；用户可在明确对象后单独选择强制停止。
- 重启保留服务身份，并生成新的运行记录。
- 后台任务的对应操作使用“重新执行”，生成新的任务运行记录。
- 操作进行中防止重复提交；失败后保留原状态、诊断信息和已完成步骤。

### 5.3 停止

- 本机服务优先正常退出，覆盖该服务相关的子进程，完成后核对进程及已知监听端口。
- 信号发送前核对当前进程身份；PID 已复用或身份无法确定时，不执行未经确认的停止。
- Docker 单容器停止和 Compose 服务停止默认保留数据。删除容器、镜像或数据卷属于独立操作，不包含在“停止”或“结束工作”中。
- Compose 整组操作显示所有成员结果；单成员操作不隐式停止其他成员。
- 项目批量操作应逐项反馈成功、失败及跳过原因，不能只显示整组成功。

## 6. 项目结束策略

### 6.1 项目配置

用两个独立触发开关表达用户确认的选择：

| 手动结束触发 | 退出 Codex 触发 | 结果 |
|---|---|---|
| 开启 | 关闭 | 点击该项目“结束工作”时停止适用服务。 |
| 关闭 | 开启 | Codex 真正退出时停止该项目适用服务。 |
| 开启 | 开启 | 任一触发发生时停止适用服务。 |
| 关闭 | 关闭 | 服务持续运行，由用户单独控制。 |

建议初始默认值为“手动结束开启、退出 Codex 关闭”，需在原型确认时确定。

### 6.2 建议的服务例外

服务默认继承项目策略，允许单独设置“持续运行”。例外优先于项目自动停止设置，仍允许用户对该服务手动点击“停止”。

适用示例：前端与后端随工作结束停止，数据库或缓存容器持续运行。该例外功能来自讨论中的建议，待确认。

### 6.3 触发语义

- “结束工作”是用户对指定项目的明确动作，区别于一个聊天完成回复。
- “退出 Codex”指应用真正退出，区别于关闭窗口、切换聊天、回复结束或聊天归档。
- `SessionEnd` 只能作为辅助证据；其事件语义不能直接用作应用退出判定。
- 同一项目有多个聊天时，单个聊天结束不触发项目整体停止。
- 手动结束只影响指定项目；退出应用时分别计算各项目自己的策略和服务例外。
- 应用崩溃、强制退出、多个 Codex 实例以及 Mac 关机的处理方式尚未确认，不能在实现中静默扩展成同一种触发。

用户退出 Codex 后，负责停止服务的管理组件必须仍能执行操作；不能依赖已经退出的界面或模型继续处理。

## 7. 建议交互设计

### 7.1 菜单栏

- 显示运行中的服务数量和需要关注的状态。
- 展示项目与服务概要，可打开服务地址、停止或重启指定服务。
- 提供打开主窗口的入口；复杂配置与历史查询进入主窗口。

### 7.2 主窗口

| 区域 | 信息与操作 |
|---|---|
| 项目列表 | 项目名称、工作目录/worktree、运行数量、异常摘要。 |
| 服务列表 | 服务名称、类型、管理状态、运行状态、健康状态、端口/地址、运行时长。 |
| 服务详情 | 项目归属、启动配置、进程或容器身份、控制操作、最近错误与日志。 |
| 历史 | 每次运行的起止时间、结果、退出信息和关联日志。 |
| 项目设置 | 两种结束触发开关；服务例外；建议的批量操作入口。 |

关闭主窗口后，建议保留菜单栏和服务管理能力。退出管理应用时是否一并停止服务，需要明确设置，不能与“退出 Codex”的策略混淆。

## 8. 持久化与日志要求

至少保存以下信息；具体数据库和结构由实现设计决定，现有 SQLite 仅为验证原型。

| 对象 | 主要字段 |
|---|---|
| 项目 | ID、名称、规范化工作目录、可获取的仓库/worktree 信息、结束策略。 |
| 服务 | ID、项目 ID、名称、类型、来源、管理能力、启动配置、健康检查配置、服务例外。 |
| 运行记录 | ID、服务 ID、开始/结束时间、状态、退出码、停止原因、诊断信息、日志位置。 |
| 实际运行对象 | 进程身份及监督信息，或 Docker 容器 ID、Compose 项目/成员标识；根据类型选择。 |
| 操作记录 | 操作对象、动作、触发来源、开始/结束时间、结果及错误。 |

历史从应用开始采集时持续积累；记录存在不代表运行对象仍然存在。重新打开时应核对实际状态，不直接复用上次的“运行中”显示。

数据保存在本机。记录必要的服务配置和诊断信息，避免为服务管理收集完整聊天正文或全部环境变量。环境配置必须足以支持实际服务重启，敏感配置的保存方式在实现设计中确定。

日志需要控制总量并支持滚动保存；日志和历史保留时间尚未确认。当前第一版以定位启动、停止、重启失败为首要用途，不承诺恢复没有采集过的历史日志。

## 9. 接入设计约束与可行性状态

### 9.1 建议接入方式

采用配套插件或辅助启动入口，交由独立管理组件启动、观察和控制服务，保存运行身份、配置和日志。Hooks 用于补充聊天、项目和生命周期关联。

同时探索普通命令启动的服务发现；只有证据足够时才能自动接管，否则先展示为“已发现、未接管”。该方式尚未验证可靠性。

若 Codex 桌面自动接入无法成立，需要向用户说明覆盖范围并重新确认替代流程；不能把要求用户逐次手动登记的版本直接视为原需求已经满足。

### 9.2 第一轮验证结果

证据见 [第一轮验证报告](../validation/ROUND1_REPORT.md) 和 `hook-trust-results.json`（仅本机原始证据）。

| 能力 | 当前结论 | 不能据此推导的内容 |
|---|---|---|
| 本机服务控制 | Python、Node、Java 最小 HTTP 服务实测通过。 | 实际 Vite、Spring Boot、npm/Maven 多级启动链全部兼容。 |
| 状态与清理 | 健康与进程状态分离、子进程清理、身份不匹配拒绝停止实测通过。 | 完整生产级进程身份保证与监督进程崩溃接管。 |
| 历史与恢复 | 不同管理进程读取 SQLite，重启形成独立记录；跨两个 Codex 工具调用持续运行。 | 完整 Mac 应用或系统重启后的恢复。 |
| 后台任务 | 成功、失败、取消实测通过。 | 任意任务重新执行都不会产生重复业务效果。 |
| Docker | 单容器、Compose 成员和整组控制、测试数据保留实测通过。 | 已集成到统一服务模型及运行历史。 |
| 项目策略 | 3 项规则模拟通过。 | 真实 Codex 应用退出触发已可靠识别。 |
| Hooks 信任与加载 | 当前项目已受信任，5 个 hooks 均 trusted/enabled，项目层已加载。 | 当前桌面聊天已实际触发工具 hooks。 |
| Hooks 实际事件 | 已捕获两次 CLI 会话 SessionEnd。 | Mac 桌面应用退出、SessionStart、Stop、PreToolUse/PostToolUse 全部通过。 |
| 桌面自动登记 | 当前桌面测试命令没有对应工具事件，尚未确证。 | 可以仅依赖已配置 hooks 自动登记所有服务。 |

第一轮服务实验共 25 项检查通过，其中 22 项是真实进程/容器实验，3 项是策略模拟。上述信任审核与 CLI 生命周期检查另行记录，不混入该计数。

## 10. 第一版验收标准

以下为建议的正式验收用例。原型验证与产品验收分开记录；只有实际目标环境通过，才可标记产品能力完成。

| 编号 | 场景 | 预期结果 |
|---|---|---|
| A-01 | 在 Codex Mac 桌面应用中启动本机服务 | 服务自动登记或通过已确认的配套入口登记，项目归属正确，用户无需逐次补填正常启动信息。 |
| A-02 | 启动实际前端、Java 后端、Python 后端 | 各至少验证一个实际项目启动方式；能找到实际运行对象和访问地址，启动失败有诊断信息。 |
| A-03 | 进程存在但服务不可访问 | 展示运行中与不可用，不误报健康。 |
| A-04 | 停止带子进程的服务 | 相关进程退出，已知监听端口释放，其他项目服务不受影响。 |
| A-05 | 按原配置重启服务 | 旧运行结束后新运行启动；工作目录和必要环境正确，历史新增记录，无意外副本。 |
| A-06 | 端口冲突、命令不存在或启动失败 | 显示失败及可定位原因，不把其他占用端口的进程识别为新服务。 |
| A-07 | 运行对象身份不匹配 | 拒绝不确定对象的停止，说明原因，保留诊断记录。 |
| A-08 | 后台任务成功、失败、取消和重新执行 | 结果正确，重新执行形成独立记录，完成的任务不显示为服务异常。 |
| A-09 | 单 Docker 容器停止与重启 | 操作指定容器，状态正确，必要数据保留。 |
| A-10 | Compose 单成员与整组控制 | 作用范围正确，组与成员不重复操作，逐项展示结果。 |
| A-11 | 项目手动结束 | 按策略停止指定项目适用服务，持续运行例外及其他项目服务保留。 |
| A-12 | 关闭窗口、切换聊天、回复结束或归档 | 不被误识别为退出应用，不误停服务。 |
| A-13 | 真正退出 Codex Mac 应用 | 管理组件继续执行各项目退出策略；操作结果持久化，持续运行服务保留。 |
| A-14 | 管理界面关闭后重新打开 | 历史和配置保留，实际状态重新核对，仍可操作正确对象。 |
| A-15 | 重复点击、停止失败、批量部分失败 | 避免并发重复启动，展示单项结果及可继续采取的动作。 |
| A-16 | Docker 引擎或监督组件不可用 | 显示未知或不可控制及原因，不误报所有服务停止。 |

响应速度、轮询间隔、健康检查超时、正常退出等待时间需在实现阶段给出明确数值，再补充性能验收。当前不把讨论中未确认的数值作为承诺。

## 11. 实施顺序与交付物

| 阶段 | 主要工作 | 完成条件与交付物 |
|---|---|---|
| M1：接入补充验证 | 确认 Mac 桌面工具事件覆盖、实际启动流程、应用退出识别与管理组件独立存活。 | 输出事件时序证据和覆盖范围；确定接入路径。不能用 CLI 事件替代桌面结论。 |
| M2：统一服务管理 | 定义项目、服务、运行、操作与服务组；集成本机服务、任务、Docker 和 Compose。 | 可在统一入口完成启停、状态、历史、归属及恢复；实际项目用例通过。 |
| M3：Mac 交互原型与实现 | 根据确认的布局实现菜单栏、列表、详情、日志、历史及项目设置。 | 用户确认原型；核心流程无需进入终端即可完成日常操作。 |
| M4：结束策略与整体验收 | 集成真实应用退出检测、项目策略和服务例外，验证多项目与异常情况。 | A-01 至 A-16 逐项记录结果；未支持场景明确展示能力边界。 |

具体 UI 框架、后台组件实现方式、打包与分发方案尚未选择，不在本需求文档中预先固定。

## 12. 待确认与待验证事项

### 12.1 产品选择待确认

- 菜单栏与主窗口的具体形态；是否第一版就包含项目批量操作、未接管服务发现和持续运行例外。
- 项目结束策略的默认值，以及项目是否按 worktree 独立设置。
- 应用崩溃、强制退出、多个 Codex 实例与 Mac 关机是否触发自动停止。
- 退出管理应用时的服务处理方式，与退出 Codex 的策略分别定义。
- 后台任务“重新执行”是否对有重复副作用的任务提供明确提示。
- 日志和历史保留时间、磁盘上限、敏感环境配置保存方式。
- macOS 最低版本、硬件架构范围，以及是否需要开机启动。

这些事项可以在原型或实现设计阶段分批确认，不影响先完成 M1 的独立技术验证。

### 12.2 技术验证待完成

- 当前桌面聊天未触发工具事件的原因，以及重新加载会话后的行为。
- 普通启动命令能否可靠关联进程身份、项目/worktree、日志与启动配置。
- 配套启动入口能否覆盖真实前端、Java/Python 项目及其子进程。
- 退出 Codex 桌面应用的可靠识别机制及关闭窗口等误触发排除。
- 监督组件异常退出后对已有服务的接管，以及系统重启与睡眠唤醒的处理。
- Docker 能力接入统一状态、历史和项目策略的完整流程。

## 13. 完成定义

第一版完成应同时满足：用户确认的核心范围可在 Mac 应用中使用；正式验收记录支持目标桌面环境；状态与操作结果可信；历史可恢复；项目结束策略只作用于正确的服务。

现有验证原型、CLI 生命周期记录和已信任 hooks 是实现依据，不能单独作为第一版产品完成的证明。
