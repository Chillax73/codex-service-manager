# 使用、排障与卸载

## 快速体验

按 README 构建并打开应用后，在自己的测试项目目录通过绝对路径调用 scripts/csm。可以登记一个不监听端口的后台任务：

```sh
/path/to/codex-service-manager/scripts/csm launch --name demo-task --task -- /usr/bin/python3 -c 'import time; print("demo", flush=True); time.sleep(60)'
/path/to/codex-service-manager/scripts/csm list
```

界面可停止/重启并查看每次历史；将返回 service ID 替换到 `csm stop <serviceID>`，通过管理入口停止测试任务。界面关闭不会停止服务。

## 项目管理（开发分支）

项目右键或左侧“当前项目操作”菜单提供改名/删除。先停止或处理所有活动、未知及停止失败服务，再查看删除预览。删除仅移出列表并保存本机回收记录；底部可撤销，管理设置可恢复。恢复不启动服务，同目录或登记标识已存在时拒绝覆盖。回收记录包含原本保存的启动配置，仍需按私密本机数据保护；当前无自动过期或永久清空入口。删除项目不代表擦除凭据或删除日志。

## 查看状态与快速筛选（开发分支）

选择项目或“全部项目”后，可按全部、运行中、未运行、处理中或需关注筛选，并同时搜索服务名称和类型。运行中的服务若出现健康异常或诊断问题，仍显示运行中，并附需关注标记。详情和历史可以区分成功、取消、已停止、已退出等具体结果。

服务列表顶部提供“添加服务”“发现本机服务”和刷新。发现弹窗可选择未登记容器和归属项目，当前项目可作为初始选项。“刷新当前项目”和“刷新全部服务”分别检查相应范围内已登记的服务。窗口工具栏的齿轮打开“管理设置”。

项目栏显示全部所属服务的汇总状态和总数。有运行服务显示“运行中 N”，有异常另外显示“需关注 N”；没有运行服务时显示当前优先状态、共同静态状态或“无运行”，空项目显示“无服务”。右侧筛选为零不影响左侧项目真实运行数量。完整优先顺序见 [README](../README.md#状态颜色筛选与项目汇总020)，本轮简化状态的验证见 [体验优化验收](results/UX_0_0_3.md)。

## 排障

已出现在列表但重启禁用：查看详情中的能力原因。可靠的观察进程可直接停止；启动配置缺失时用“配置启动方式…”补齐单项命令与必要环境，保存不会重启。共享多服务启动器或未知子进程需先明确独立范围，不能强行扩大控制。停止失败只能在已确认范围内强制停止。更新采集代码后通过 `scripts/csm stop csm-auto-collector`、`scripts/csm capture-start` 恢复新版内部采集组件，不停止业务服务、不更改 hook 信任。

全局自动观察先运行 `scripts/check_capture_hooks.py` 核对两个 User config handler 的 trusted/enabled，再新建聊天验证实际启动。组件不可用时在管理设置点击“启动或恢复自动采集”。仅组件运行不代表既有聊天已重新加载 hooks。若自动审批拒绝新增的采集副作用，保留拒绝原因并正常取得明确授权，不通过移除前缀或绕过信任继续。

| 现象 | 检查和处理 |
|---|---|
| 缺少 Swift/Python 或构建失败 | 执行 `xcode-select --install`，确认 `/usr/bin/python3 --version` 和 `swiftc --version`；运行 `scripts/doctor.py`。 |
| 项目工具找不到 | npm/mvn 加入 PATH，或设置 CSM_NPM/CSM_MAVEN（可含空格）；Java 17+，必要时设置 JAVA_HOME。安装 Vite 依赖需要支持其 engines 的 Node。 |
| 服务运行但健康不可用 | 核对监听地址、端口和健康路径；查看最小日志，健康和进程存活分别显示。 |
| 端口冲突 | 查明占用者，改用空闲端口；不要直接清理未知进程。 |
| 状态未知或停止失败 | 核对实际进程/容器身份和 Docker 连通性。停止失败不能继续重启；仅对确认拥有的对象使用 UI 显式强制停止。 |
| 容器组件不可用 | 启动 Docker Desktop，检查 `docker info` 和 `docker compose version`，保留原容器和卷。 |
| 退出观察器不可用 | 设置中使用恢复入口；确认目标应用、同一状态目录和实例状态。真实退出与窗口关闭不同。 |
| 找不到之前记录 | 核对 CSM_STATE_DIR/`--root`；GUI、CLI 和观察器应使用同一目录。 |
| 项目仍显示运行中，但服务列表为空 | 核对当前项目、状态筛选和搜索词；项目汇总统计全部所属服务，列表只展示同时符合条件的对象。 |
| 首次 Maven/Node 测试失败 | 先运行 `scripts/prepare_fixtures.py`，检查网络和工具版本；Maven 初次运行仍可能下载插件依赖。 |

## 另一个聊天或窗口启动服务却没有记录

1. 核对实际状态。检查目标端口、PID/出生身份或指定容器状态；完成回复或旧 PID 文件不能证明服务仍在运行。已退出对象不能补录为运行中，也不要先重启来制造登记证据。
2. 在目标项目目录运行 `/usr/bin/python3 /path/to/codex-service-manager/scripts/check_capture_hooks.py /项目目录`，确认两个 User config handler 为 trusted/enabled。这个独立配置探测不会重载桌面或证明旧聊天接入。未信任或定义变化时，在正常 `/hooks` 中逐项审核。
3. 查看“管理设置 → 服务自动采集”的心跳与错误，必要时使用恢复入口。组件正常但无新事件，继续检查该聊天是否在安装前已打开、工具是否经过 shell hooks；新窗口复用旧聊天仍可能漏记。
4. 当前使用新聊天验证常见路径，或让后续需完整控制的服务通过 scripts/csm 登记。已经运行的进程不要重复启动；已有容器在身份和项目明确时用 `csm container` 登记，已有 Compose 要使用原项目名，不能创建副本。
5. 首阶段没有无 hook 的后台自动登记兜底，也没有已验收的旧聊天配置热加载操作。复杂包装、脚本内部 Docker 和采样前完全脱离的进程可能漏记；原生发现列表的候选不能等同自动观察或接管。

不要将退出/重启 Codex 作为无副作用的配置刷新：真正退出可能触发已管理项目的退出策略。自动观察不改变业务进程的存活方式，也不负责补回日志、退出码或启动配置。旧聊天加载、后台兜底与复杂脚本控制分别见 T16–T18，不通过修改信任状态文件或放宽审批实现。

## 项目采集开关与历史保留

选择具体项目，打开“管理设置 → 采集此目录中的 Codex 启动”；关闭后可继续显式登记，既有观察与服务继续保留。CLI 为 `scripts/csm capture-policy --cwd /path/to/project --enabled off`，恢复改为 `on`。按规范化 cwd 精确匹配，子目录和 worktree 独立；需使用更新后的采集代码，旧版已安装 handler 不会自动获得新策略。

管理设置显示最近采集故障的阶段/异常类型，不保存异常正文；它是最近一次记录，不等于持续故障。PostToolUse 发现缺失 arm 时记录 checkpoint 故障，若回调本身缺失则不能保证提示。结合实际事件、心跳和 [Hook 边界说明](HOOKS.md#命令边界与项目级禁用) 排查，不能用心跳正常推断所有聊天已覆盖。

“清理旧历史”接受 1–36500 的整数天数，显式删除超过期限的已结束旧运行/操作记录与未被跟踪的过期采集事件；保留每项最近运行、活动运行和项目回收档案。仅删除本工具日志目录中与运行 ID 对应的普通日志，跳过外部路径和符号链接。默认不自动清理，不停止服务，不操作源码/容器/卷；也不保证 SQLite 空闲页或系统备份中的内容被安全擦除。

## 卸载与数据清理

曾启用全局自动观察时，先在 `/hooks` 逐项禁用本工具两个 User config handler，执行 `/usr/bin/python3 scripts/install_global_capture.py --remove --instructions`，确认加载过旧配置的聊天不再执行本工具回调，并通过 `scripts/csm stop csm-auto-collector` 停止本工具的内部采集任务。不要停止仅观察的业务进程。此后再按下面步骤处理配套入口、观察器和数据。

1. 在 UI/CLI 中逐项停止自己希望结束的服务；持续运行的服务和保留例外需明确决定。`end <projectID>`遵循项目开关，不保证停掉保留例外。不要用旧 PID 直接 kill。
2. 在每个接入项目执行 `/usr/bin/python3 /path/to/codex-service-manager/scripts/integrate.py /path/to/project --remove`。它只移除标记段落，保留其他指令；检查首次备份 AGENTS.md.csm-backup。原型 hooks 如曾安装，检查项目 .codex/hooks.json，将指向 validation/hook_recorder.py 的本工具条目逐项移除，保留其他 hooks；勿删除整个混合配置。
3. 在设置中查看状态目录。退出管理应用后独立退出观察器仍可能存活；用活动监视器检查 ServiceManager 的完整命令及 `--watch --root`，仅退出属于本工具、同一状态目录的观察器。不要按名称批量 kill，不要退出其他状态目录或项目的对象。
4. 确认没有登记服务/观察器在使用数据后，备份需要保留的历史，再通过 Finder 删除 `~/Library/Application Support/Codex Service Manager/`（自定义 CSM_STATE_DIR 以实际配置为准）。删除数据库不会自动停止服务，不要边运行边删除。
5. 删除本地 `.app` 与源码目录。容器、镜像和卷不会随卸载删除；仅在确认归属和数据已备份后用 Docker 的显式命令单独处理。

升级前退出旧版管理应用和自动采集组件，保留业务服务。备份完整状态目录，包含 SQLite 数据及其 WAL 文件。重新构建后让同版本的应用、引擎和采集器使用同一状态目录。

新版引擎首次打开数据库时在独立架构锁内完成事务迁移。项目和服务的首次登记时间从最早留存运行估算，缺少证据的记录显示未知。项目自动扫描默认开启，旧项目默认不置顶。迁移失败时事务回滚，应用可在问题修正后重试。

回退时先单独备份新版状态，再用升级前的完整备份与对应旧版应用恢复。使用独立测试状态目录验证迁移和恢复流程。

### 项目自动扫描

项目操作菜单可暂停或恢复单个项目的自动扫描。侧栏“扫描管理”提供“全部启用”“全部暂停”，也可勾选项目后操作。“全部”作用于执行时已登记的项目，以后首次发现的新项目默认开启。暂停后，新服务发现与已有服务的后台状态检查同时停止。管理器保留最近一次检查结果，并显示检查时间。手动刷新只执行一次检查，保持扫描偏好。启停和删除仍会核对真实状态。

CLI 使用 `scripts/csm project-scan <项目 ID> off` 暂停，使用 `on` 恢复。运行 `scripts/csm refresh <项目 ID>` 手动刷新该项目，省略项目 ID 则刷新全部项目。验证时给命令传入 `--root <测试状态目录>`，从相同目录的 `list` 输出获取项目 ID。

### 项目与服务排序

项目栏可按名称、项目创建时间或运行中的服务数排序，三种规则均支持升降序。默认使用名称升序。项目右键菜单可置顶或取消置顶。置顶组和普通组分别按所选规则排序，“全部项目”入口固定在最上方。偏好与置顶状态随状态库保存，暂停项目沿用最近一次检查结果。

服务列表先显示运行中服务，同组按服务首次登记时间从新到旧排列。单项目、全部项目、搜索与状态筛选使用相同顺序。重启保留原登记时间。

### 服务名称、配置和删除

从服务行右键菜单或详情可修改名称、编辑配置或删除登记。名称立即生效，服务 ID 与历史随原登记保留。启动和健康配置保存在待生效配置中，下次成功启动时应用。重启会先核验并停止旧运行。

本机进程和任务支持编辑命令、工作目录、环境变量与健康地址。已有环境仅显示键名，可按键更新或明确删除。Docker 和 Compose 支持修改名称、健康地址和删除登记，容器的启动参数由原配置管理。

删除前会核对实时状态，并提示受影响的运行和操作记录。先手动停止运行中的服务，再删除登记。源码、容器、卷和日志保留。登记与历史移入本机私密回收记录，启用扫描的项目可再次采集到符合条件的服务。
