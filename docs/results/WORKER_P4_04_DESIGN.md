# 后台观察剩余 CPU：诊断与下一步方案

2026-11-15。诊断基线：代码 e3c9ce4，部署记录 01f310d；正式应用已安装 P4-02。此次只诊断与设计，P4-04～06 尚未实施。任务状态以 [tasks](../../specs/001-service-manager/tasks.md) 为准。

## 实测结论

后台观察的约 29% 可以复现。主因是历史容器/Compose 的逐条外部查询，尤其是不存在容器仍持续轮询；Python 侧另有连接、写回和快照处理成本。P4-02 主要复用了采集器与本地进程观察的查询，尚未合并容器查询。

先测正式进程，再做独立重放，避免把剖析进程的开销算入基线。2026-11-15 01:46:55～01:47:58，六段各约 10 秒 CPU 差分，100% 为占满一个 CPU 核；子进程为已回收子进程的累计 CPU，不是活动监视器单个 Python 行的读数。

| 组件 | 自身 CPU | 子进程 CPU | 合计 |
|---|---:|---:|---:|
| snapshot-worker | 9.53% | 18.55% | **28.08%** |
| collector | 2.84% | 12.09% | 14.93% |
| GUI | 2.24% | 0% | 2.24% |

worker 约 66% 的 CPU 来自子进程。采样末尾可读取的四个核心传感器均值 42.64°C、最高 43.36°C；温度受整机负载影响，此数据不能证明全部热量由 worker 产生。

## 代码与负载证据

### 1. 关闭采集不等于暂停历史服务观察

[capture.set_policy](../../backend/capture.py) 更新 `capture_disabled_cwds`，约束自动采集；[observation_schedule._projection_sql](../../backend/observation_schedule.py) 的观察资格使用 `projects.auto_scan=1`，排除内部组件，但不读取采集禁用目录。

现场 26 个已登记项目的 auto_scan 全部为 1，符合观察条件的服务共 1,035 条：当前项目 100 条，其他 25 个项目 935 条。其他 25 个已登记项目均在已有的 61 个禁用采集目录内。因此其他项目没有被重新打开采集，但旧记录仍在刷新。这是两个策略的当前语义，不能通过暗中暂停其他项目来声称性能优化。

### 2. 不存在、停止状态的容器仍有密集 N+1 查询

[observation.interval](../../backend/observation.py) 及持久化 SQL 截止时间先判断 unknown，再判断 Docker 类型，最后才判断普通终态。窗口可见时，unknown 每 16 秒，其他 container/compose 每 7 秒；隐藏时分别 32/20 秒。停止容器不会进入普通终态的 120/240 秒分支。

现场 Docker 类记录 53 条：48 个独立容器登记，加 5 个 Compose 成员登记；48 个容器 ID 中 40 个已不在实际清单，8 个仍存在且当前停止或失败。5 个 Compose 成员属于 2 个 `(project, file, cwd)` 组，分别有 3、2 个成员。现有 26 个真实容器包含上述 8 个，其余并不对应这 48 条登记。

`probe_observation → containers_for` 每条独立执行：普通容器一次 inspect；Compose 每成员一次 `compose ps -aq member`，再逐 ID inspect。`container_observation(*ids)` 虽已支持多个 ID，当前 worker 调用仍逐条；统一 command 包装遇非零退出直接抛错，不能直接拼接所有 ID 就认为批量错误语义已解决。

32.14 秒正式缓存观察中，unknown 容器更新时间变化 68 次，停止/失败容器 32 次，停止 Compose 23 次，说明这条路径确实持续运行。短命子进程的轮询采样只提供下界，不用它推算准确命令总量。

独立诊断进程通过只读数据库重放当前 `containers_for`，仅允许 inspect/compose ps，连续三遍均为 **58 条命令**：13 次成功 inspect、40 次失败 inspect、5 次 compose ps。没有调用生命周期操作或写回正式记录。

| 外部查询 | 单次子进程 CPU 均值 | 单次墙钟均值 |
|---|---:|---:|
| inspect 成功 | 22.47 ms | 21.58 ms |
| inspect 失败 | 22.62 ms | 29.46 ms |
| compose ps | 81.66 ms | 76.91 ms |

三遍各消耗约 1.60、1.62、1.60 秒子进程 CPU。按当前 7/16 秒频率估算，这些 Docker 命令约相当于 **15.67 个单核 CPU 百分点**；这是串行重放与频率模型，不能当作正式 18.55% 子进程 CPU 的精确分账。缺失 ID 结论来自清单比较和缓存错误类型；重放脚本的区分大小写关键字标记不作为缺失判定依据。

### 3. SQLite 连接、重复写回是第二层成本

`prepare_observation/finish_observation/reconcile_docker_unlocked` 的读取、身份复核、运行协调和缓存持久化仍会多次打开连接；无变化的 Docker 运行状态也可能再次更新。每个到期批次还创建新的 ThreadPoolExecutor。

将正式只读数据复制到私有内存 SQLite 后，对代表记录各重放 10 次：准备与完成合计每条有 2～5 次连接；Compose 准备中位约 3.95 ms、完成约 0.77 ms，普通终态完成约 0.30 ms。内存夹具不等于生产磁盘性能，不能拿它直接分配剩余 CPU。正式 worker 的 5 秒原生栈采样同时出现大量 SQLite schema 初始化/prepare/close 路径，支持连接开销方向，但含等待和递归栈，不能把栈计数解释成 CPU 百分比。

### 4. 快照仍全量加工，但不是 29% 的首要来源

正式数据只读重放，六次去掉首轮后的中位值：

| 路径 | CPU/次 | 响应体积 | 返回条目 |
|---|---:|---:|---:|
| list-v1 | 37.08 ms | 约 1.05 MB | 1,035 |
| menu-v1 | 31.13 ms | 约 17.4 KB | 16 |

`snapshot_cached` 对所有记录解析并计算 `detail_revision`，最后才截取菜单前 16 条。菜单体积已减小，计算量仍接近全量。列表约每 2 秒一次，对应直接 CPU 成本约 1.85 个百分点；菜单每 10 秒约 0.31 个百分点。到期选择查询中位仅 0.341 ms，当前不是优先热点。以上为组件重放，不能与正式各项简单相加得出完整 CPU 分账。

## 推荐顺序和实现边界

### P4-04：同批容器/Compose 查询合并，优先实施

位置：`backend/observation.py` 批次编排、`backend/engine.py` 只读 Docker 探测。依赖：本诊断与批量查询错误契约验证。

1. 保持当前观察范围、刷新间隔、最多 12 条到期批次与最多 6 个工作线程。只合并本批到期记录；不为了凑批扩大为全库查询。
2. 按实际 Docker 连接配置分组，按 Compose 的项目、配置文件、cwd 和有效调用配置进一步分组。只有等价连接/调用配置才能共享结果，不记录凭据或完整环境。Compose 按成员集合查询，再合并需要 inspect 的 ID；继续发现外部重建后的新 ID。
3. 使用最小字段格式：当前身份、状态、端口、必要错误字段及 Compose project/service/working_dir/config_files 标签；不取 Env 或健康日志。Docker 官方支持 [inspect 多对象](https://docs.docker.com/reference/cli/docker/inspect/) 和 [Compose ps 多成员](https://docs.docker.com/reference/cli/docker/compose/ps/)，但混合有效/缺失 ID 的失败行为仍须真实契约测试。
4. 每个 ID 独立返回存在、已确认缺失或查询失败。命令非零时保留能校验的有效对象，不能一项不存在导致整批丢失，也不能把 daemon 不可达误报成全部消失。必要时每连接上下文最多补一次清单查询，禁止退回每 ID 重试风暴；不确定则保留查询失败。
5. 上下文仅在当前批次有效，携带采样时间和服务/运行/项目策略版本；最终写锁内复核保留，版本变化跳过旧结果或新鲜重查。控制路径始终实时检查身份，不使用观察缓存。
6. 保留 4 秒有界探测预算，外部调用期间不持有写事务。按连接组限制批量故障影响；批次结果分别写回，不把一个容器的错误扩散到其他对象。

命令数量验收：正常每连接批次至多一次合并 inspect，Compose ps 至多每等价组一次；故障补查有界。现场 5 个成员分属 2 组说明有合并机会，但截止时间可能错开，不能预先承诺每个真实周期必定由 5 次减成 2 次。必须覆盖集中到期和错峰到期。

### P4-05：复用连接并减少无变化的写回

依赖 P4-04 完成后的重新剖析。按线程拥有读取连接，写入由明确的写线程/上下文拥有，禁止在六个线程间共享裸 SQLite 连接；状态根变化、异常及退出显式释放。外部查询前结束读事务，保留每服务最终复核和原子写入。

跳过相同 runtime/state 的重复运行更新，但继续维护 checked_at、健康、新鲜度与必要的调度变化；验证新运行与外部状态变化不会被吞掉。只有证据表明值得时才复用线程池。完成条件包含连接次数、CPU、RSS、写入量和退出延迟对照，不能只验证连接减少。

### P4-06：按返回范围构建摘要并复用稳定内容

依赖 P4-05 后的剩余成本评估。menu 只为实际返回的 16 条构建详情版本与条目内容，全局/项目统计仍覆盖全部服务；list 按服务内容版本复用稳定摘要。checked_at、过期提示、策略与选中详情必须正确失效。完成条件包括 full/list/menu 语义等价、真实窗口/菜单行为及 CPU/响应量对照。

### 暂不采用的策略变化

不自动把采集禁用目录映射为观察暂停，不删除历史记录；“仅刷新当前项目、其他项目保留缓存”是另一个产品取舍，不是本轮优化默认项。

缺失对象退避可以后续评估，但必须区分已确认缺失与 daemon 故障；停止容器还可能外部重启，不能直接全部改成 120 秒。若将来修改刷新策略，须同步 `observation.interval` 与持久化 SQL view；当前 `ensure` 仅首次创建，单改 Python 或 SQL 模板不会迁移已有数据库。需要版本化迁移、旧状态兼容和回退测试。

## 规格细化后的架构与契约

本节为后续 self-spec 细化；前述诊断数据仍是 P4-D2 历史实测，本次没有重新采样或执行 PoC。需求与准入唯一入口为 [spec](../../specs/001-service-manager/spec.md) 的 P4-04～06 增量规格。

### 职责与状态归属

| 位置 | 目标职责 | 允许共享的内容与生命周期 |
|---|---|---|
| observation.observe_due | 在 observation.lock 内选择最多 12 个到期服务，编排分组和最多 6 个执行线程，收集结果后逐服务完成 | 一批候选与不可变探测结果；批次结束释放 |
| engine Docker 只读适配 | 构造保持原执行语义的命令、解析逐对象结果、验证 Compose 归属，不写业务状态 | 同批对象结果；禁止传入 start/stop/restart 等控制入口 |
| engine prepare/check/finish | 捕获服务/运行/策略版本，最终检查并生成运行与观察投影 | SQLite 为登记和历史权威；Docker 为外部实际状态来源 |
| engine/storage 连接上下文 | 批次内按线程建立读连接，协调线程拥有写连接；负责关闭、回滚与根隔离 | 连接不跨线程、不跨 ROOT 或数据库文件身份，不缓存 SELECT 结果 |
| snapshot_cached / observation.serve | 同一数据库读事务内生成协议响应，serve 拥有可丢弃摘要缓存 | 单 worker 内存缓存；不写数据库，不跨进程，不用于控制 |
| Swift Store/Infrastructure | 消费原有协议、处理迟到详情和 UI 刷新 | 不新增前端状态来源或刷新定时器 |

继续使用现有进程边界；不引入常驻 Docker events 订阅、HTTP Docker SDK、数据库连接池服务或额外 writer 线程。避免扩大部署和凭据边界。`engine` 的共享读工具保持兼容，批量适配仅从后台调用；显式 observe/手动刷新与控制仍可走原路径。

### D-04：逐对象批量结果（推荐待 V-01 验证）

内部结果概念字段为 `service_version/run_version/policy_token`、`started/checked_at`、`objects_by_id`、`errors_by_id` 和 `members_to_ids`。不成为公共 RPC 或落盘格式。完成时复核完整服务/最新运行内容及项目创建/策略代际，并沿用 started 与较新缓存时间比较；不能只比较 config_revision。

执行顺序：捕获本批候选版本 → 不持有数据库事务地按等价调用配置分组 → Compose 成员发现 → 合并 inspect → 按服务组装结果 → 最终复核和持久化。独立组的超时不抹除其他已完成结果。同批外部读操作共享 4 秒单调时钟预算；Compose 发现阶段最多使用前 2.5 秒，为健康组的 inspect 和必要清单补查预留时间。所有查询共享同一个时钟截止点，最多 6 个执行槽，不因排队或补查重置。该分段使超时的 Compose 发现不能耗尽其他组的 inspect 预算；极慢或排队过久的发现保持 unknown，按现有节奏重试。

分组必须保持现有调用语义：`containers_for` 的 Compose ps 使用 runtime_env(spec)/cwd，而随后 inspect 当前使用 docker 默认调用环境，不能借优化擅自给 inspect 改用 Compose 环境。只有可证明执行上下文等价的请求才合并，显式 env/env_unset 差异保守分组；环境内容仅按现有命令调用传递，不写诊断、缓存键日志或响应。无法证明等价时分组隔离，不声称仍能合成一次命令。

Compose 发现结果须保留 ID→成员的最小映射，正常空成员和查询失败严格区分；优先使用最小格式输出而非包含 Command/环境的完整 JSON。实际支持的格式在 V-01 验证。inspect 对容器类型查询，保留返回 ID 与要求 ID 的严格对应；有效 JSON、必要状态字段和标签均通过才算可用。不接受前缀碰撞、重复冲突对象或其他 Docker 对象类型作为容器。

| 内部结果 | 对服务的外部行为 |
|---|---|
| 容器存在且字段/身份有效 | 正常计算状态、健康、能力及运行历史 |
| 独立容器 ID 确认缺失 | 维持 unknown 与问题说明，objects=None；不把空列表交给运行协调器结束历史 |
| Compose 发现成功且某成员无容器 | 允许该成员的空对象列表，沿用现有空成员协调语义 |
| Compose 已发现 ID 但 inspect 缺失/无效 | 该成员 unknown，不以残缺对象列表结束或重建运行；其他有完整映射、完整结果的成员继续成功 |
| daemon 错误、超时、无效/不完整输出 | 受影响项 unknown；不把失败解释成缺失，不修改其运行历史 |

非零退出时逐行保留可验证的有效对象；未返回对象最多用同调用上下文的一次成功清单查询确认缺失，不解析本地化 stderr 作为唯一缺失依据。清单成功也不能让“清单存在但 inspect 没返回”的对象变成正常；保持 unknown。Compose 成员映射不能验证时整个受影响 Compose 组失败，其他组和独立容器不受影响。诊断只保留现有脱敏问题语义，不发布完整 stdout/stderr。

正常调用数上限以实际等价组计：每组发现至多一次，每 inspect 上下文至多一次；只有确需分片的参数/输出容量限制可增加有界分片，验收须单列，不能以“分片”恢复每 ID 命令。发生版本变化时丢弃结果、保持待重新检查；不在同批循环单项重试。候选数不等于容器数，Compose 多副本、字段异常和大输出必须覆盖，沿用或收紧已有超时/协议边界，不加载 Env/健康日志。

V-01：在隔离注册表和自有 Docker/Compose 资源中记录客户端/Compose 版本，验证“有效+缺失+全部缺失”、最小成员映射、多副本、成功空成员、错误返回、模板字段缺省和 ID 对应。通过标准是能够在既定预算/命令边界内可靠区分完整结果与失败，且不丢正常邻项。部分输出或映射无法可靠取得时暂停 worker 接入，重评“成功清单预筛选+批量 inspect”的有界备选及命令预算；先修订设计，不默默退化。纯适配契约验证可先行，不能把生产 Docker daemon 停机当故障注入手段。

### D-05：批次拥有连接，单服务事务写回（已选定）

采用批次生命周期而非无限期线程池。准备阶段按执行线程复用一个 query-only、自动提交的读上下文；同线程处理多个候选，嵌套 prepare 复用已有上下文。协调线程按批次拥有一个写连接；缓存快照连接仍由 serve 线程独立拥有。这样连接数量随执行线程而非逐服务增长，代价是下一批仍需打开连接，但不增加常驻线程与长期事务管理。

写路径显式传递内部 db 参数至最终 check、运行协调和 persist；普通 CLI 调用保留默认自行开关连接的兼容入口。不能让已有 query-only 线程局部上下文截获写事务内的最新读取，也不能使 new_run/set_run 隐式另开连接提交一半结果。

对可能改变运行的结果，锁顺序固定为现有 mutation_lock → 每服务 reconcile 锁 → BEGIN IMMEDIATE → 最终复核 → 运行变化与投影写入 → 提交 → 释放。只改缓存的路径继续 BEGIN IMMEDIATE 内复核和写入，无须增加 mutation_lock。禁止已持有 SQLite 写事务再等待应用锁；显式控制保留原有身份核验与锁规则。监督器不依赖 mutation_lock，其更新必须被事务中的版本复核识别。

同一服务一次提交：失败全部回滚；其他服务已提交结果不撤销。遇现有忙锁语义则保留旧缓存，后续调度重试；不得在锁内执行 Docker、网络或睡眠重试。提交失败不返回 state_fresh=True，不推进 checked_at。异常/批次完成显式 close；文件身份/ROOT 改变时终止上下文并重新初始化，不能沿旧文件继续写。

去重只比较将写入的实际字段，runtime 按结构语义比较；不省略新的 started_at、ID、退出码、结束时间、健康/错误等变化。无变化时跳过 runs UPDATE，但仍推进观察 checked_at 并触发既有截止时间维护。不得用缓存相同为理由压掉真实新运行或重写历史 started/ended。验收须覆盖写到一半的异常、监督器竞争、删除/恢复同 ID 和跨 ROOT 嵌套。

Python 实际解释器 3.9.6、SQLite 3.43.2（本次只读版本检查），构建目标 macOS 13+、Swift 5。不使用仅新 Python 才有的 autocommit API；沿用 isolation_level 和显式事务，保留默认线程归属检查。连接上下文负责事务而不会自动 close，因此关闭由明确的 finally/closing 保证。依据 [Python 3.9 sqlite3 官方契约](https://docs.python.org/3.9/library/sqlite3.html)（2026-11-15 核对），不把此版本检查当作所有 macOS 环境兼容证明。

### D-06：精确内容失效，动态时间独立计算（已选定）

每次响应仍在一个 SQLite 读事务内取登记、观察和元数据，先生成所有服务的最小统计/排序信息，再按现有 `running 优先、created_at 降序、id` 顺序选菜单前 16 条。不能在 SNAPSHOT_ROWS 的按 name 排序结果上先 LIMIT 16。项目侧栏、总数、健康/需关注、has_cached/has_paused 均覆盖全部适用服务；menu 项目列表仍按现有返回条目过滤。

缓存由 serve 持有并显式传入 snapshot_cached；独立 CLI 和 full 格式保留无缓存兼容路径。以状态根/数据库文件身份、服务 ID 和 detail_revision 所有输入字段的精确原值比较判断内容变化，不以 checked_at 或 PRAGMA data_version 充当内容版本。不变才复用解析后稳定内容和原 detail_revision；改变则按既有算法重新生成，保持迟到详情校验兼容。

每次生成新响应对象，重新叠加 checked_at、now、visible、paused、state_fresh/cache_state；不修改共享缓存对象，也不缓存最终 JSON。窗口模式切换、时间越过过期阈值、组件心跳失效、项目重命名/排序/删除等元数据变化即使服务内容未变也应体现在当前响应。删除服务条目及时淘汰，删除后恢复同 ID 重新核对全部版本。

不跨进程共享，不持久化，不用长 TTL 掩盖失效。工程容量上限暂定 5,000 项且估计驻留字节 16 MiB，先到者触发 LRU 淘汰；单项超限跳过缓存并正常计算，冷启动或淘汰只影响成本。该上限基于既有 5,000 条规模测试作为可调实现参数，不是实测内存承诺；估算须覆盖原值、解码对象和摘要，另测 RSS。ROOT/数据库文件身份变化、重连或格式不兼容时清空。无需新增 schema 或定时清理任务。

### 运行、兼容与回退

三阶段沿用数据库 schema、SQL view/触发器和 RPC 版本；内存缓存丢弃即可恢复，不迁移生产数据。测试同时覆盖旧 full、新 list/menu 调用者及旧进程并存写入；显式控制不得依赖新缓存存在。实现后先独立状态回归与匹配 CPU 对照，再按单独部署授权替换应用和管理组件，不操作业务服务。回退只替换程序、重建内存上下文，不能回滚用户最新登记或运行历史。

选型取舍：Docker CLI 合并优于引入 SDK/长订阅，因为能沿用当前调用和部署边界；批次连接优于常驻连接池，因为足以先消除条目级重复且退出生命周期明确；精确内容比较优于纯 TTL/每次全量哈希，因为保持动态新鲜度且不引入持久版本迁移。实际收益是待测结论，若无稳定改善应缩小或撤回相应优化，不扩大技术栈。
