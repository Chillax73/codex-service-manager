# 采集器启用后的 CPU 诊断与 P4 方案

2026-11-14。运行版本为 420f379 对应的已安装应用。本文完成诊断与设计，P4 生产代码尚未实施；只读 SQL 重放不是完整实现或回归通过的证明。

## 启用范围

用户授权启用 hooks 和采集器，明确只开启当前项目。恢复 PreToolUse/PostToolUse 定义和 features.hooks，沿用正常审核的信任状态；通过 app-server 查询确认两项均 enabled/trusted，并核验当前项目、当前聊天产生的新采集事件。原 62 个禁用目录中只移除当前项目，其余 61 个保持关闭。采集器经 csm 登记启动，未停止或重启业务服务。

目录开关控制后续 hook 采集；既有服务观察及已经确认的跟踪后代不因此自动消失。不能把“61 个目录关闭”解释成不再读取这些目录既有服务的任何状态。

## 实测

CPU 以单核 100% 计。使用 libproc rusage 的区间增量，分别计算进程自身和已回收子进程 CPU；Mach tick 按本机 125/3 转换，两项均用 getrusage 独立校准。不同持续进程的自身 CPU 与父进程的已回收子进程 CPU 分开计数。

| 对象 | 关闭基线 30 秒：自身 / 子进程 | 启用后 60 秒：自身 / 子进程 |
| --- | --- | --- |
| 采集器 | 未运行 | 52.25% / 9.90% |
| 后台观察 worker | 10.74% / 18.88% | 15.96% / 20.47% |
| 原生界面 | 1.50% / 0% | 1.62% / 0% |

采集器及其短命子进程合计 62.15%，worker 合计 36.43%。采集器平均 RSS 50.15 MiB、物理 footprint 42.96 MiB，60 秒归属磁盘写入仅 8 KiB；现有证据指向 CPU 重复计算，不支持内存膨胀或采集器大量写盘为主因。worker 同期归属写入约 30.71 MiB，需单独归因，不能把它算成采集器写入。

随后独立 15 秒交叉检查：采集器自身 54.80%、子进程 10.33%；worker 自身 9.80%、子进程 17.83%；界面 1.54%；OrbStack helper 14.07%、Codex renderer 4.04%。峰值附近另一次 ps 瞬时显示后两者约 47%/52%，不是上述窗口均值。

AppleSMC 四个性能核心：关闭基线各次平均约 48.61–57.39°C；启用采样最高单核心 91.99°C。14:44:25（北京时间）采集器仍开启，核心平均已回到 49.05°C、最高 50.07°C。两组时长、其他应用负载与热状态不同，不能据此声称采集器独自导致全部升温，或用两次温差估计优化后的降温量。

## 已定位的主瓶颈

`backend/capture.py:collect_once` 读取全部开启观察的 observed 登记，再对每条调用 `engine.service` 和 `engine.latest`，之后才筛选本地、运行中且未结束的服务。`backend/engine.py:query` 每次新开 SQLite 连接。采集器保留的一个连接仅用于维持 WAL，没有供这些查询复用。

生产数据库只读重放相同查询/筛选路径的结果：

| 路径 | 检查登记数 | SQLite 连接数 | CPU | 墙钟时间 | 符合条件的服务数 |
| --- | --- | --- | --- | --- | --- |
| 现有逐条查询 | 925 | 1,851 | 583.267 ms | 594.470 ms | 0 |
| 联表预筛选原型 | 同一数据集 | 1 | 1.739 ms | 1.740 ms | 0 |

两者候选 ID 集合一致。原型仅验证这个零候选现场的读取子路径，约 99.7% 的下降不能外推为完整采集器收益；非零候选、并发改变和最终写入仍待实现与回归。

cProfile 中 SQLite execute 约 392 ms、connect 约 81 ms，JSON 解码约 8 ms。真实进程两秒采样也出现 sqlite3InitOne、SQL schema 解析和分配热点。P3 增加了到期索引的 view/triggers，新连接需要解析更复杂的 schema；尚未做移除 schema 的隔离对照，不能单独量化其放大幅度。P3 的事件文件缓存和到期选择没有覆盖这段全量逐条查询，不能继续把旧事件 JSON 重读认定为当前主因。

活跃轮次末尾等待 0.5 秒；仅上述约 0.58 秒 CPU 的无效工作就足以解释约半个核心的占用数量级，与实测相符。

## 次要成本与证据边界

`capture.managed_processes` 仍遍历登记并逐条读取运行/身份；`engine.probe_observation` 对 observed 进程查身份，运行状态下还调用 `adoption.stop_plan`。后者未传入上下文时会再次查询全机进程、跟踪元数据，并可能查询监听端口。它们解释了可优化的短命命令来源，但没有逐调用计数证据，暂不分摊 9.90%/20.47% 子进程 CPU。

当时 39 条未结束 observed 运行的 control_members/launch_members 均为空，不能声称大成员数组遍历是本次主因。后台 worker 的整体成本也不能全归到这一条代码路径。

## P4 实施顺序（待授权实施）

1. **P4-01：消除历史登记的逐条查询。** 将 kind、最新运行、running、ended 条件下推到单次批量查询，返回候选所需字段后再解析。最新运行选择必须与 engine.latest 保持一致。仅当有效跟踪集合为空时跳过 scope/recipe 补全，不跳过 Docker 时间窗、观察调度或心跳。对非空候选尽早匹配跟踪 PID 和事件。保持写锁内项目代际、服务、运行及出生身份的最新复核；查询快照不得成为控制授权。
2. **P4-02：复用同轮读取和身份探测。** 先测 P4-01 剩余成本，再引入有界、线程独占的读取上下文，并批量获取 observed 根身份。向适用的展示能力计算传递同轮 process table、tracking、listeners，减少重复 ps/lsof。不得跨六个探测线程共享一个裸 SQLite 连接，不得在外部命令或网络等待期间持有读取事务。真正停止/重启继续实时复核，不复用过期展示结果；查询失败保持保守语义。
3. **P4-03：完整启用状态验收。** 固定相邻版本、数据库和可控 hook 负载，预热后交替三轮、每轮 120 秒，分别覆盖窗口/菜单、无活动与活动跟踪；同时记录自身和已回收子进程 CPU、连接/外部命令次数、RSS/footprint、写入、检测延迟、温度和其他进程负载。真实业务状态只核验，不为制造负载而停止或重启。温度只作辅助观察，不作为唯一通过标准。

首轮工程目标：1,000 条历史记录、零候选时查询连接数保持 O(1)、读取子路径 CPU <10 ms；相同启用负载下采集器含短命子进程 CPU 较基线降低至少 80%。这是待验证目标，不是已达成承诺；如果未达标，按剩余剖析结果继续归因。不通过删除历史、降低身份保护或盲目延长所有刷新周期达标。

回归覆盖 260/1,000/5,000 条历史，零/单/多活动候选，latest 选择一致性，运行切换、项目暂停恢复、并发删除、PID 复用、迟到探测、Docker 关联窗口、后代跟踪与采集器重启。候选结果与旧路径对照；最终变更仍须通过进程、采集、策略、缓存、调度、迁移相关测试。核验 hook 检查点成功、关联不丢失且延迟不劣于同负载基线，其他 61 个禁用目录集合不变。原始诊断数据保留在 ignored 测试状态目录，不提交本机进程/项目明细。
