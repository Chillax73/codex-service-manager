# 用户级服务自动观察：首阶段本机结果

本文保留首阶段只读验收结果。后续按能力接管、启动配置与启停验证见 [普通启动接管](ORDINARY_ADOPTION.md)。

日期：2026-10-12（Asia/Shanghai）。这是开发分支的新增能力，未包含在 v0.1.0 标签。用户已确认先自动显示，复杂脚本的控制和重启另行补齐。

## 已交付

一次安装用户级 PreToolUse/PostToolUse hooks，经正常逐项审核后，新本机聊天的常见 shell 启动流程自动记录服务。无需逐项目 AGENTS.md 或逐次登记。独立采集器由 scripts/csm 作为内部任务管理，通过临时 FIFO 获取 shell 身份，在约 0.5 秒的采样中跟踪后代；末尾检查点覆盖常见 nohup 后台启动，无端口叶子任务持续 30 秒后显示。

自动观察对象在原生列表、项目归属、运行数量、详情和历史中显示。它们不参与停止、重启或结束策略；后端同样拒绝控制。Docker 观察只读取容器身份、状态、端口和指定 Compose 标签，不读取完整环境及健康日志。

## 验证结果

| 类别 | 结果与边界 |
|---|---|
| 自动采集进程集成 | 8 组通过：直接/exec、脚本多服务、nohup、持续任务、归属/去重、身份/历史、输出/退出码、组件恢复及安装保留。输入 hooks 是显式标注的测试输入，实际进程与组件均真实运行。 |
| Docker/Compose | 6 项断言通过，真实创建单容器及两个 Compose 成员、实际重启、观察字段白名单、去重和原有容器状态不变。不是桌面 Docker 回调证据。 |
| 实际桌面 | 一个没有项目指令的新聊天，实际代码模式 exec_command 启动两个 HTTP 服务和一个任务；原生窗口自动显示正确项目及“3 个运行中”，观察标识和禁用控制可见。 |
| 用户级配置 | 三个不同项目目录均列出两个 user/trusted/enabled handler。配置证据不替代实际事件；已有聊天没有自动热加载的保证。 |
| 原生恢复与退出 | 设置中真实停止提示和恢复按钮成功；正常退出管理界面后旧 UI 进程消失，同一采集组件存活，界面可重开。 |
| 原有功能回归 | 14 组进程、13 组项目管理、9 组端点/时间/日志契约通过；最终应用重新构建并检查实际窗口。 |

## 当前边界

仅覆盖本机、已加载并启用 hooks 的 shell 工具路径。启用前的服务不被事后认领；远端、专门绕过 hooks 的工具以及在采样前已完全脱离已知父进程的特殊脚本可能漏记。直接 Docker 返回的容器 ID、直接 Compose 的配置/标签匹配已验证；复杂包装及脚本内部 Docker 操作尚未可靠覆盖。原本未采集的本机 stdout/stderr、退出码、完整环境和重启配置无法补回。

菜单栏共享能力字段，没有逐个重新点击观察对象的快捷控制；窗口关闭后新增服务未另建夹具复测。常见路径首阶段已部署，不作所有项目、工具、脚本百分之百覆盖声明。

## 旧聊天复查与剩余工作

安装前的旧聊天在另一窗口后续启动服务，未产生新的全局采集事件，也没有 arm 检查点。同期用户级配置已列出两个 trusted/enabled handler、采集器心跳正常。因此安装、审核与后台组件正常不足以证明旧聊天已加载 hooks；新窗口继续同一聊天没有解决。

`check_capture_hooks.py` 使用独立短时 app-server 读取配置，不连接桌面共享运行时。正常旧聊天配置重载尚未实施或验收，没有可发布为已验证步骤的重载命令。新聊天是当前已验证路径；后台发现兜底仍未实现，“任意聊天”需求不能标为全部完成。

本次业务现场复查时，聊天声称运行的七个本机服务没有目标 TCP 监听，两个容器已退出；未把它们补录为运行中或重启。未确认退出原因，不能从当前状态推导历史。当前采集器不负责维持被观察业务进程的存活。

剩余任务：T16/G-08 旧聊天正常配置加载；T17/G-09 可信来源与归属的后台发现兜底；T18/G-10 复杂脚本的控制与重启。详见 [规格](../../specs/001-service-manager/spec.md)、[任务](../../specs/001-service-manager/tasks.md) 和 [验收](../../specs/001-service-manager/acceptance.md)。
