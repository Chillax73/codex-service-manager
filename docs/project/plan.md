## P4-04～06 · 后台观察实施计划

本阶段依据 [W-REQ-01～06](spec.md) 与 [D-04～06、W-01～04](worker-observation-design.md)。本节保留任务依赖、完成条件与验证方法。

P4-04 与 P4-05 已完成阶段验收，接续工作从 [P4-06-A](#p4-06-a--确认摘要热点并冻结协议基线) 开始，先复核摘要热点并冻结协议基线。阶段进度在 [任务清单](tasks.md#p4-d2--后台观察诊断与后续任务) 更新。下文保留各阶段的原有依赖与验证条件。

### 共用实施与验证约束

- 编码前只读核对正式组件的实际脚本/模块入口。此前正式采集器引用当前仓库 backend；如仍如此，优先复用未被正式组件引用的现有 checkout/worktree，无合适目录时使用 create_worktree 建立隔离实施目录，分支沿用 `f-wqx-` 前缀。不改正式采集器入口、不重启它来腾出目录，也不把未验收代码写回正式源码入口。此项归入 P4-04-A/B 的准备工作，二者复用同一隔离成果。
- 开始和结束记录当前 hooks 指纹、当前项目采集启用、其他 61 个目录禁用、管理组件身份/心跳、正式业务身份和容器状态/启动时间/重启计数。只读核验；不暂停历史项目观察、不控制业务。原始记录仅留 ignored 目录，报告发布聚合结果。外部主动变化如实说明。
- 测试自动创建独立状态根、唯一服务名/Compose 项目名及所有权标签；长期测试进程通过 csm，容器/Compose 按项目规则登记。清理核对身份/标签，只清理测试所有资源；失败时保留精确残留记录，不全局 kill/prune。不能关闭生产 Docker daemon 来制造故障。
- 每阶段先保留相邻基线的源码/后端/构建与内容指纹，再改实现。CPU 矩阵两版使用同一测试驱动、同一夹具/模式/事件；合成检查点注明来源，不冒充真实桌面 hook。不将旧 P4-03 的 HTTP 负载结果当作本轮 Docker 对照。
- 核心正确性失败先返工；性能测量必须运行，未运行不能以 WARN 代替。已测但收益不稳定或资源/延迟恶化如实 WARN，不宣称达成；每阶段 self-review 后按约定本地提交，不推送、不安装到 /Applications。

### P4-04-A · 验证批量外部契约，解除 V-01

- 位置/成果：扩展 `tests/verify_docker.py`、`tests/verify_docker_failures.py` 的自有资源检查，必要的可复用夹具放 tests/support 或专属测试辅助文件；仅验证与适配契约，不提前接入 worker。关联 D-04、W-REQ-01/02/05，W-01a/b/c。
- 依赖：P4-S 规格与隔离准备；不依赖其他实现任务。
- 完成条件：在实际 Docker/Compose 上验证有效+缺失、全部缺失、最小 ID→成员映射、多副本、成功空成员、字段缺省/身份对应；记录 CLI/Compose 版本、退出码分类、计数、脱敏结果。错误/超时用测试端点或受控命令替身验证适配边界，与真实引擎证据区分。
- 必需验证：有效对象不随邻项缺失丢弃；缺失/错误与空成员可可靠区分，预算和有界补查可实现，资源清理通过。通过后据证据更新 spec 的局部准入；失败则保持 P4-04-C 阻塞，按 D-04 重评有界清单预筛选并修订规格，不绕过验证。A 自身可完成时不等待完整 W-01 产品接入验收。

### P4-04-B · 建立可复验 Docker 负载与相邻基线

- 位置/成果：扩展 `scripts/benchmark_probe_pipeline.py`、适用的测试夹具与 `docs/TESTING.md`；保留原 HTTP 模式。新增 Docker 场景入口须实现后记录真实 CLI 参数，本计划不把尚不存在的参数当可运行命令。关联 W-REQ-06、W-04a/b。
- 依赖：P4-S 与隔离准备，可与 A 独立推进。
- 完成条件：脚本自动准备约 1,035 条记录（40 个自有已删除容器 ID、8 个停止/失败记录、5 个 Compose 成员/2 组及普通终态），支持额外自有活动容器、集中/错峰到期，固定种子/规模。缺失 ID 不借用生产清单；镜像按既有测试选择并核验可用，缺失依赖明确报告。
- 必需验证：原版/原版短冒烟确认启动、真实窗口/菜单模式、计数/CPU 子进程归属、输出、失败后清理均可信；冒烟不作为 CPU 改善证据。保存正式 P4-04 相邻基线的构建/源码指纹，准备 W-04 完整运行。正式基线优先记录当前代码提交（规格提交仅文档变化），不能仅凭“P4-02”标签猜版本。

### P4-04-C · 批量探测接入后台并保留旧控制路径

- 位置/成果：`backend/observation.py`、`backend/engine.py`，扩展 `tests/test_probe_reuse.py` 或新增聚焦批量契约测试；按 D-04 完成分组、最小结果、剩余预算、逐对象错误和版本绑定。关联 W-REQ-01/02/05，W-01、W-02a。
- 依赖：A 的 V-01 通过；不依赖完整性能矩阵。
- 完成条件：只合并同批等价调用，保留 12/6 上限与现有调度；独立容器缺失为 unknown，Compose 只有成功完整空成员才可传空对象；跨上下文不混用，变化版本丢弃，不形成逐项重试风暴。显式 observe/控制入口不消费批量缓存。
- 必需验证：隔离契约覆盖正常/部分失败/损坏输出/超时、配置/运行/暂停代际变化；检查调用计数符合 D-04，静态核对实际控制调用链。C 的完成表示实现及针对性回归通过，完整 W-01/W-04 由 D 收口。

### P4-04-D · 真实链路、性能与阶段验收

- 位置/成果：现有真实 Docker/Compose、观察/采集/缓存/真实进程回归入口，B 的矩阵驱动；聚合验收报告拟写 `docs/results/WORKER_P4_04.md`（实施时创建）。关联 W-01、W-02a、W-04。
- 依赖：B、C 完成。
- 完成条件：W-01a/b/c 真实与隔离故障证据齐备；外部重建、多副本、归属冲突、错峰到期及策略竞争通过；执行下述三组四场景完整相邻对照，记录命令减少是否转化为总 CPU 改善。构建/签名与真实窗口模式检查通过，正式范围/身份核验及测试清理完成。
- 提交点：P4-04 阶段自审覆盖 A～D，提交该阶段实现、必要测试/驱动和聚合报告；不夹带 P4-05/06。必要验证受阻时保留待完成；正确性失败重开 C 或对应夹具任务，不把协议问题归为性能 WARN。

### P4-05-A · 复核剩余连接和写回热点

- 位置/成果：复用 P4-04 的计数、短时剖析与隔离组件重放，记录拟议报告 `docs/results/WORKER_P4_05.md` 的基线部分。关联 D-05、W-REQ-03/06、W-04。
- 依赖：P4-04 阶段验收并提交。
- 完成条件：按每批/线程/服务区分连接数量，区分 runs 更新与 checked_at 更新，量化自身/子进程 CPU 和写入；冻结 P4-04 相邻基线。若热点已消失或成本不足，明确保留/缩小方案的依据并只修订受影响设计，不凭旧诊断硬套优化，也不自动将 P4-05 勾选完成。
- 必需验证：计数不改变事务/线程语义，重放不会写正式状态；估算与实际采样分列。不得要求后续实现先完成才能取得此基线。

### P4-05-B · 实现批次连接、单服务原子写回及去重

- 位置/成果：`backend/engine.py`、`backend/observation.py`，必要时 storage 连接工具；扩展 `tests/test_probe_reuse.py`、`tests/test_observation_policy.py` 与缓存测试。关联 D-05、W-REQ-03/05、W-02a/b/c。
- 依赖：A 证据支持当前或已修订的 D-05。
- 完成条件：线程拥有只读连接、协调线程拥有写连接；按既有锁顺序在单服务短事务中完成最终复核、运行更新与缓存提交；内部 db 参数贯穿运行写入，无隐式旁路提交。无变化运行不写 UPDATE，检查时间及调度仍推进；异常显式回滚/关闭，旧 CLI 调用兼容。
- 必需验证：真实隔离 SQLite 中注入“运行更新后、缓存提交前”异常，断言全部回滚；测试监督器竞争、根/文件替换、跨线程误用、嵌套上下文、删除恢复同 ID、真实新运行不被去重。针对性回归通过后 B 可完成，不等待 C 的性能证据。

### P4-05-C · 回归写回语义并验证资源收益

- 位置/成果：真实进程、Docker/Compose、策略/缓存回归及共用矩阵；完成 `docs/results/WORKER_P4_05.md`。关联 W-02、W-04，并复验受共享 engine 变化影响的 W-01。
- 依赖：B 完成，基线取 A 冻结版本。
- 完成条件：旧/新写入者共存、忙锁/失败恢复、退出与新运行历史通过；连接计数随线程而非服务增长，测量批次结束连接关闭。完整 CPU 对照同时披露 RSS、写入和退出延迟，不能以连接下降单独宣称成功；业务边界和清理通过。
- 提交点：P4-05 自审 A～C 后本地提交本阶段代码/测试/报告；出现一致性失败重开 B，只有测量不足则补 C，不重置已有效的前置证据。

矩阵每阶段三组 AB/BA/AB，共六轮，四场景为窗口/菜单 × 无活动/有活动 Docker 混合负载，每场景预热后正式计 120 秒，总测量段 48 分钟/阶段（不含准备、预热、回归和清理，不是交付工时承诺）。无活动仍包含 53 条 Docker 历史检查；有活动额外加入自有普通容器与 Compose 成员，固定数量/副本并写入证据。CPU 测量前初始化完成；状态/版本/模式断言失败的样本保留失败记录但不混入有效对照。修正驱动时两版同改并重跑受影响的配对。

记录 GUI/worker/collector 自身与已回收子进程 CPU、命令种类与组数、SQLite 连接/运行 UPDATE、RSS/footprint/磁盘写入、刷新/退出延迟、模式与资源身份。温度可读时作为环境数据记录，不作为功能门禁或唯一 CPU 收益证据。每阶段对每场景分别展示三对结果和聚合，正常/故障命令计数与 D-04 的上限对应。性能无稳定改善则 WARN，必要正确性失败 FAIL，必要运行未取得证据保持受阻。
